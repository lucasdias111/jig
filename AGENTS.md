# AGENTS.md

Jig is a macOS-first code editor (it also builds on Linux and Windows) where AI works through a coding agent called up at the cursor, not through a chat or an IDE somewhere else. You select code, press ⌘K and say what you want; the agent works in a small conversation beside the code, and each edit it wants shows inline for you to accept or reject. The agent reads this file, so keep it short and current.

## The concept

**AI as a tool, not a colleague.** IDE refactorings are precise but fixed; agents are open-ended but take you away from the code. Jig keeps the refactoring interaction, anchored to the code you point at and reviewed edit by edit, with an agent behind it. The name is from woodworking: a jig guides precise, repeatable cuts by hand; Jig is that guide for the agent. All AI goes through the agent: there are no one-shot model calls and no saved prompts of Jig's own for the user to pick (an agent's own commands and skills, called "agent commands", stand in for those). The one exception is the Map's actions (Index Domains, Update Domains, splitting a domain, Explain this level, a sketch's Make Task and Implement): Jig-written instructions, each starting a normal, visible conversation, as delegating a todo does; there's no user-editable prompt library.

Principles:

- **Near the code.** In Code mode, interactions are anchored to the cursor. Agent mode offers an explicit full-screen conversation. No side panels, except an agent conversation you pin to the side yourself.
- **You decide.** Every change is previewed and needs an explicit accept. Nothing reaches the disk unreviewed (unless you accept the rest of an agent conversation's edits with ⌘↩), and the agent's shell commands, web access and subagents wait for a go-ahead too.
- **Keyboard first.** Few shortcuts, each obvious.
- **Clean and Mac-like.** The code is the interface. Restrained colour, floating panels, follows system light/dark.

### Workspace modes

The centered top-bar switch shows Code, Planner, Map and Agent (⌘1, ⌘2, ⌘3, ⌘4; Ctrl outside macOS). Planner uses the remote's basic tasks: title, Markdown description and todo checklist, stored in `.jig/tasks/`, with task editing and delegation to the agent. It fills the editor area and retains its expanded tasks and scroll position between modes. Esc returns to Code; task links open Code and Go Back returns to Planner. File tabs show only in Code and use ⌃1–9 on macOS, Alt-1–9 elsewhere. There are no job boards, factory presets, project settings or isolated job runs. Agent mode fills the workspace with the current conversation, a multiline composer (Enter sends, Shift-Enter adds a line), model selection, Choose agent, Conversations, New conversation and Stop. It uses the same agent sessions, history and permissions as Code; switching modes retains the transcript and draft. With no conversation selected, Agent mode shows the selected agent’s recent conversations for the project, newest first, above a persistent message composer; clicking a conversation resumes it, while sending a message starts a new one. Typing and switching modes preserve the draft without selecting a conversation. New conversation remains available while a conversation is open. Shell/web/subagent requests stay on the page; edits open Code for the usual explicit review, with Go Back returning to Agent. Esc stops a running turn or answers a pending request, and preserves an idle conversation.

### The agent

The input (⌘K) starts or picks up a conversation with the agent. The agent has its own colour (theme info, orange) and icon (bot) everywhere it appears: input, highlight, buttons, conversation tag.

- **Agents.** A coding-agent harness at the code, agnostic about the agent: Settings > Agent picks it from the agents listed as data (`agents.rs`; `assets/default-agents.toml` has OpenCode, Claude Code, Codex and Gemini CLI and documents every field; the user's `agents.toml` adds any agent that speaks the Agent Client Protocol, or replaces one by `key`; Install runs its `install` into Jig's agents folder, whose `node_modules/.bin` and `bin` are searched with the PATH; `[agent] use` in `settings.toml`). OpenCode (`kind = "opencode"`, the default) runs through Jig's own client (`opencode serve`, `jig-ai/src/agent/opencode.rs`), with the model picked under it on the Agent page (other agents bring their own model and sign-in, which the page says), edits always set to ask and questions with choices. Every other agent runs over ACP (`jig-ai/src/agent/acp.rs`): one process per agent, JSON-RPC on stdio, Jig as a client that reads files from disk and writes them only after review (`fs/write_text_file`; an edit already allowed by permission is written without asking twice). An agent that answers "Authentication required" (`acp::SignInNeeded`) gets its sign-in methods offered in the conversation: a `terminal` one opens the system terminal with the agent's own login (`agent::open_in_terminal`, a `.command` file on macOS), then Enter tries again; any other is `authenticate`d, and the turn is sent again. `jig-ai/src/agent/harness.rs` puts both behind one `Backend`/`Session`, and `jig-ai/src/agent.rs` holds the types every agent shares. The agent reads and edits the whole project with its own skills, commands and instructions file. Each edit it asks about (OpenCode's diff; ACP's permission request with a `diff` or the tool's old and new text; or a file it hands Jig to write) arrives *before* it's written and opens in its file's tab as a normal preview. An ACP agent set to edit without asking can't be stopped; the transcript says "Edited x without asking". The built-ins are set up to ask: Claude Code's default mode does, Codex starts `read-only`. Enter/Tab accepts (OpenCode writes it), Esc/⌘Z rejects (the agent is told and may retry). ⌘↩ accepts it and the rest of the conversation's edits (`AgentRun::accept_edits`): each is then written without opening its tab and listed as edited, except in a file with unsaved changes, which the agent is told to leave alone, as before. The conversation is `Workspace::chat`; a short note (`Workspace::note`, such as why nothing can run) shows apart from it, and Esc dismisses the note first. While it's docked, ⌘K still opens the input at the code, for another conversation or an earlier one. Starting another conversation replaces the one on screen, undoing an edit of its still under review. A conversation belongs to the project, not the file it started from: it works in the folder open in the sidebar (or the file's repository when there's none, `Workspace::agent_project`), its header names that project, and it stays open and working across tab switches; an edit it proposed waits in its file's tab (Esc or clicking the file in the conversation goes back to it, and accepting it settles it there). A saved file isn't needed once a folder is open. The run is a floating conversation at the code (`jig-commands/src/chat.rs`): what was asked, the agent's replies, each edit taken or rejected, and a reply box once the agent answers. It opens centred in the window's right half and top to bottom at the height it grows to (`ChatFrame::full_height`), whatever code it's about (`Workspace::agent_anchor`, `Workspace::right_centre`). Its header shows the model it runs on: clicking it lists the agent's models (OpenCode's from the providers, an ACP agent's own) and picks one for the rest of the conversation, an ACP agent switched at once with `session/set_config_option`; a conversation keeps the agent it started with. Drag it by its header to move it (it then stays put) or by its corner to resize it; its pin button docks it to the window's right edge, full height, beside the code, on the editor's own background; docked, its left edge drags to resize it, and the next conversation opens docked at that width until it's unpinned. Replies render Markdown, and code they mention is a link: the agent is asked to link it (``[`name`](path#L12)``, `jig_ai::agent::prompt`), and files it names without one, `` `src/a.rs:42` `` or bare, are linked when they exist (`jig_planner::link_files`); a click opens the code, or flies the Map there while it shows (`Workspace::open_agent_link`). The transcript has a scrollbar and keeps to its end while scrolled there (a long reply's Markdown is laid out a frame late, `chat::follow_the_end`); scrolled up, it stays put and shows a More below button. A reply continues the same OpenCode session, and a reply like `/review main` runs that OpenCode command in it. Shell commands, web fetches and searches, and subagents (`task`) ask by default, except a shell command that only reads the project (`jig_ai::agent::read_only`: `ls`, `cat`, `grep`, `rg`, `find`, `sed -n`, `git log` and the like, piped or chained, writing nowhere but `/dev/null` and naming no existing path outside the project), which goes ahead; Settings > Agent (`settings_window/agent_page.rs`, `[agent]` in `settings.toml`, `jig_ai::agent::Permissions`) sets each to ask, allow or don't allow, and turns the question tool off. The rules are re-sent to OpenCode at the start of every turn, so a change applies from the next one, earlier conversations included; edits always ask and outside the project is always denied. Asked, the conversation shows what it wants to run with three buttons: Allow (Enter/Tab, once), Always allow (⌘↩; OpenCode's `always` reply, naming the patterns it will remember, or an ACP agent's `allow_always` option; an agent with neither has Jig allow that kind of request for the rest of the conversation) and Deny (Esc). What ran is listed in the transcript either way; two or more calls in a row fold into one "Used N tools" row that a click opens (`chat::transcript_rows`), while an edit made without asking always shows. Over ACP, the settings map onto tool kinds (`execute` is shell, `fetch` the web, reading and searching need no go-ahead, anything else asks). With OpenCode's question tool on (the default): the question shows with numbered options, answered by clicking one or typing a number or your own words in the reply box (Esc declines). Edits and requests from its subagents come through the same way. Each subagent has a row of its own in the transcript (`ChatEntry::Subagent`: what it was given, how many tools it used, a spinner while it works), which a click opens to what it did, reading included, and the report it gave back; its words don't go into the agent's reply. Subagents are told apart by the session each runs in: OpenCode's child sessions (the `task` tool's `sessionId`, its output the report), and over ACP the draft's subagent sessions (Jig declares `clientCapabilities.subagents`; `subagent_spawned` and `subagent_state_update` on the conversation's session, the subagent's own updates and requests on its own, handed to the conversation's listener, `Connection::subagents`). An ACP agent without them shows its subagents' work as its own. Nothing outside the project. Esc in the code, once a completion list or snippet is closed, rejects an edit under review there, else stops the agent's turn; Esc again closes the conversation. From the Files or Git view, Esc focuses the current mode and closes the conversation only if it's idle (`Workspace::leave_sidebar`). Edits the agent asks for at once are shown one after another. Each edit's row in the transcript counts the lines it added and removed, and a click opens its diff (`diff::edit_lines`). 15-60 s.
- **Earlier conversations.** Every conversation stays with its agent. OpenCode's are titled with what was first asked (`metadata.jig`; older Jig sessions are known by their edit-asks rule, and the user's own OpenCode sessions aren't listed). An ACP agent's come from `session/list` with its own titles, and are picked up with `session/load`, as far as the agent can; its `/` commands are the ones it last announced (`available_commands_update`), so they show once a conversation with it has started. The input lists them under **Conversations**, latest first, filtered by the typed words; Enter on one picks it up with its transcript (`Backend::open`, `history` reads it back). ⌥⌘K (Agent Conversations…, in the Edit menu and Settings > Keyboard) and the conversation's history button open the input.
- **Tasks.** A basic task checklist in Planner mode (⌘2 or ⌃⇧T, the `jig-planner` crate, its `planner/…` paths below under `crates/jig-planner/src/`, and `workspace/planner.rs`): tasks with a title, a Markdown description and a todo list, one file each in the project's `.jig/tasks/<id>.md` (`# Title`, the description, `## Todo` with `- [ ]` items; `jig-ai/src/tasks.rs`). Each is a card: click it to fold it open, check todos off or add one under it; hovering its header shows Edit and Move to Trash, open or not. + or View > New Task… and Edit open the form as a sheet over the window (`planner/form.rs`); typing `@` in its description or a todo lists the project's declarations and files (`planner/symbols.rs`, found by the shapes declarations take, so it works without a language server; with nothing typed, the open file's names), and picking one puts in its link. Hovering a todo shows an Agent button that delegates that step (`Workspace::delegate_todo`): it starts a conversation as a typed message would, with the whole task as context (`Task::step_context`, the step marked). The code the step links to is opened first and is what the conversation is about, else the selection; the agent checks the step off with `update_task` when done. A card's hover actions also hand the whole task to the agent (`Workspace::implement_task`, `Task::context`), to work through its open todos in order, checking each off. Agents make them through a tool: `Jig --tasks-mcp` is a stdio MCP server (`tasks/mcp.rs`) with `create_task`, `list_tasks` and `update_task`, handed to OpenCode in its config (started in the project's folder; its tools are `jig_*`) and to ACP agents in `session/new` and `session/load` with `--project`. Its instructions and Jig's system prompt tell the agent to write plans as numbered lists, to propose one as a task with `create_task` whenever it proposes three or more steps or work across several files rather than asking in its reply, to keep a task short (a summary, then `### Background`, `### Context`, `### Purpose` and `### Risks`, a sentence or two each, then the todos), and to link every code reference as ``[`name`](path#L12)``. `create_task` is the question: its go-ahead shows in the conversation as Save this plan as a task?, with the title and todos (`TaskDraft`, OpenCode's from the tool part's input, kept by call, an ACP agent's from the request's `rawInput`), Save (Enter) and Don't save (Esc); words typed in the reply box turn it down with them as a note (OpenCode's reply `message`; an ACP agent, which only hears it was turned down, gets them as the next message once its turn ends, `AgentRun::follow_up`), and it has no Always allow. Settings > Agent's Tasks row (`Permissions::tasks`, Allow by default) decides whether updating tasks waits for Allow; Don't allow turns saving off too (`Permissions::creating_tasks`); over ACP the tool is known by its title (`mcp__jig__create_task`). The folder is watched (just `.jig/tasks` and its parents), so a task an agent makes appears at once, opened, with a dot on the top-bar Planner segment while the view is hidden. Clicking a link opens the file at the name nearest the line (`planner/links.rs`), so links survive edits; web links open in the browser. Go Back and Go Forward (⌃- and ⌃⇧-, Alt-arrows off macOS, or a mouse's back and forward buttons; `workspace/navigation.rs`) return across jumps: task links, Go to Definition, Go to Line, problems and Find in Files results.

- **The Map.** One canvas you zoom out to from anywhere in the code, for understanding and deciding: it never changes code (the `jig-map` crate; its `map/…` paths below are under `crates/jig-map/src/`). Levels: **Code** (the editor) → **Plan** → **Site** → **Domain**. ⌘B (View > Show Map, or the title bar's Map segment left of the Agent button, which reads Code while the Map shows) or a pinch-out in the code (`Workspace::pinch_code`) shows it in place of the code (`workspace/map.rs`; one `MapView` per workspace, on the project the file's in: the sidebar's folder, else the nearest folder with `.git` or a manifest, `index::root_of`), flown out of the function at the cursor to its Plan with that box selected (you are here). **Plan** (`map/plan.rs`, laid out by `map/layout.rs`) is a neighbourhood around a focus, never the whole project: a function's callers left and callees right, one hop, at most 8 a side before "+N more", a side's tests folded into one box, packages outside one box each, hubs as badges, further hops opened by a box's ◀ N and N ▶ buttons; or a module's (a folder `dir/`, a file, or `path#Type`, entered from Site) functions framed by type, called ones right of their callers, with calls in and out at the edges; or a file the index can't read (Svelte, Vue, a page, a stylesheet; `plan::unread_file`) as one box with its kind, lines and size and "Its functions can't be read yet", the files importing it on the left and those it imports on the right, one box and arrow per file, same-named files told apart by their folders (`map/files.rs`: the read files' imports and the import lines of files it can't read, `$lib`, path aliases and root paths resolved, and a file beside it with its name, as `+page.server.js` by `+page.svelte`, linked too); Enter, a double click or zooming in on it opens its code, on another file its Plan. A box shows the function's name and compact signature (`plan::signature`); resting on it peeks at its code. Calls are arrows, dashed when only a guess by name, solid when the index or the language server (`callHierarchy`, asked about the focus, `MapEvent::AskServer`) is sure. Entering another function re-centres: its box stays put, the others glide, new ones fade in and those out of range fade where they were. **Site** (`map/site.rs`) is Domain zoomed into: the same regions in the same places (Domain takes their rects from Site, `DomainLevel::of`), each holding only its own share of the code (`Site::of` over the domains showing, so before Index Domains over Jig's drafts): its components (the deepest folder with a manifest, else the top folder), then their modules and folders, then files, and a file's types only where several have functions. A component in several domains shows in each with its own slice (`backend › bookings` in Bookings, the frontend's booking routes beside it). Folders that only lead somewhere fold away: a chain of single folders, `src`, `main`, `java` (`BOILERPLATE`), a component holding one folder (`balladeby-backend › bookings`), a folder holding one file; a Java file is its type's box. Laid out once, every box at the size its contents take (a file as wide as its title), so opening one only shows what's inside: a box starts opening at `Node::open_at`, once it's wide enough on screen and a typical box inside would read (or by 700 px), what's inside fading in (`view/scene.rs`, `site_scene`). A closed box shows its title (two lines), its purpose from its README or doc comment (`outline::file_purpose`, `index::readme_purpose`) or else what's inside by name, and how much it holds; a frame's title fits its bar. Inside a region, arrows join only boxes side by side (`Site::arrows`: each call drawn between the two siblings holding its ends, summed, thicker with more, the calls listed on hover); with a box selected, the arrows carrying its calls (or its insides') light up and the rest fade (`Site::arrows_of`, `Arrow::lit`). Calls between regions are never drawn or counted: between domains there's only their one link per pair, as at Domain, and only the selected domain's links (the domain selected, or the one holding the box selected, `selected_region`) say what flows along them. The picked domain is lit in its own colour (`RegionBox::lit`: a thicker outline and a stronger fill, at Domain too), its links drawn thicker in that colour, each box headed by the domain at the other end in that one's colour, its lines read from the picked domain's side (→ out, ← in; `picked_link`), and a box moved off its link joined back to it by a line in the link's colour ending in a dot on it. Tests (`site::is_test`) are left out until the header's Tests switch shows them (`Show`). Files the index can't read (Svelte, templates, other languages, `OTHER_SOURCES`) are placed like the rest, and zooming into one goes to its Plan. **Moving** (`map/view/zoom.rs`): pinch or ⌘-scroll zooms within a level; past a threshold it cross-fades to the next (`Transition::cross_fade`: the old level drawn fading out as the new one fades in, the box entered growing into its contents, or what's left shrinking into the box holding it), and a gesture that crossed zooms no further until it's let go, except between Domain and Site, which are one zoom, so a pinch carries straight on (`Transition::carry_on`). Plan steps out to Site at about half its size, or a little under where a big Plan starts (`plan_out`); Site steps out to Domain once the region under the pointer starts closing (`leaves_site`, `SITE_TO_DOMAIN`, a little under Domain's way in, `DOMAIN_TO_SITE`). ⌘+ and ⌘- (the code font's keys) zoom the Map a step at a time while it shows, gliding, and on past a level's end as a pinch would; ⌘0 puts the level back as it starts (`zoom_step`, `zoom_reset`). Zooming out of Plan goes to Site, onto the folder holding where you were with that box selected and its neighbours in view (`camera_on_site_box`, no closer than natural size), inside the domain holding it; Domain and Site are one zoom: zooming into a region far enough that it opens is Site, and zooming out of Site until no region in view is open is Domain, the region in the middle selected, the view staying put both ways (`MapView::continuous`); zooming in at Site over a file or type goes to its Plan, over a Plan's function to its Plan, and over the Plan's own function into its code. ⌘↑ and ⌘↓ step a level the same way, Enter or a double click enters the selected box (a region or folder flies in until it fills the view, open), the ruler in the canvas's top right (`view/ruler.rs`: Code · Plan · Site · Domain marked from in to out, its needle at how far out you are, sliding from halfway to the level inside to halfway to the one outside as you zoom, so the next level shows coming; over the code too while a pinch there heads out, its needle reaching halfway to Plan as the Map shows and carrying on from there, `Workspace::pinch_ruler`) goes to a level its name or a click near it names, Esc clears the selection and then goes back to the code, and anything that focuses the code shows it again. Dragging moves a Plan's boxes (Site's stay where the project puts them), right or middle drag pans, and Tidy lays a Plan out afresh. Entering the Map, each level stepped into and each re-centring is a place for Go Back (`navigation::Place::Map`); zooming within a level isn't. Each view keeps its dragged places, opened hops and viewport in `.jig/map/places.json`, which Jig adds to `.jig/.gitignore`. Files, Go to File and the sidebar open code; the Map is a zoom away. **Index** (`map/index.rs`, `map/outline.rs`): every Rust, JavaScript, TypeScript (and TSX), Python, Go, Java, C, C++, Swift and Zig file outlined with tree-sitter on a background thread (functions with contracts and calls, types, imports, purposes; `outline/syntax.rs` lists functions, and each language's `Syntax` in `outline/lang/<lang>.rs` says how it lists them and which of its nodes are calls), calls resolved by name, narrowed by declared types, imports and owners; read again file by file, keeping what unchanged files read as (`Project::read_again`). `big_project_live` (`JIG_MAP_PROJECT=<repo>`, `--release -- --ignored --nocapture`) checks that reading, laying out Site and a frame stay within budget on ~10k files; `map_of_jig_live` (`-- --ignored`) draws the Map of Jig itself, and `map_pictures_live` (`JIG_MAP_ROOT`, `JIG_MAP_FILE`, `JIG_MAP_AT`, `JIG_PICTURES`, `-- --ignored --nocapture`) renders a project's Plan, Site and Domain at stepped zooms, Domain as a 1600 by 1000 window shows it, and a zoom from Domain down into the Plan as PNGs, with Export Image's drawing, to check the design without a screen. **Debugger** on Plan (`map/debug.rs`): paused, the function and its callers down the stack light up as a path, and a pause in a function not on the Plan shows its Plan (`Workspace::refresh_map_debug` hands over the frames); running, each function on the Plan gets a logpoint on its first statement (`logMessage` in `setBreakpoints`, `jig-fired <id>`, kept out of the console; `workspace/live.rs`), so it glows as it's entered and the call it came along lights with a pulse; the header's Live switch turns that off. Stepping happens in the code. **Domain** (`map/domains.rs`, `map/domains/`, `view/domain.rs`, `view/domain_draw.rs`): the project as business areas, each a big region in its own colour, sized by what it holds at Site, its name above its top edge in that colour, never cut short (smaller, then on more lines, to fit the room above it, `domain_draw::name_label`), and inside only how much it holds, its full purpose and offers (`domains/level.rs`; zooming in, ⌘↓ or Enter goes to Site there); one labelled link per pair of domains, its label in the gaps, covering no region, name or other label, with a faint line back to the link when it had to move off it (`draw::label_spot`), placed once and kept in the drawing while that spot stays clear and near its link, so it moves with the view rather than jumping about (`sticky_spot`), in full on the selected domain's links and very faint, without a box, on the rest (`Arrow::faint`; Export Image draws them all in full); Shared and Unsorted greyer, apart below. Every file has one home: whichever domain or Shared names it most closely (`path#Type` over its file over its folders, deeper first, `Domains::home_of`), else it's Unsorted. Before any domains are saved it shows Jig's own grouping as dashed drafts (`domains/grouping.rs`: top folders, opened while fewer than three and wherever one holds most of the code, loose files joining the folder of their name or the group they call most, labelled by their functions' commonest words, each group's two strongest call links as flows) under a banner: "Index Domains to name and describe these". **Index Domains** (banner, header, View menu) and **Update Domains** (header, View menu, when files are Unsorted), and Split… on a selected domain, start a normal conversation (`MapEvent::Ask`, `Workspace::start_map_action`, `AgentRun::map_action`; instructions in `domains/actions.rs`): Index hands over the grouping with every source file, the index's unread ones too (just the groups past 600 files), and asks for plain offers, no routes; Update lists only the unsorted files with the saved domains. The agent works with the Map's tools and its own reading and searching, never a shell or subagents, so nothing waits for a go-ahead (`domains/tools.rs`): `map_project` gives Jig's outline (the grouping, every source file, each file's purpose, types, functions, imports and calls, narrowed by group or folder, paged), and it answers by calling `map_propose_domains` with typed fields (`action`; domains, flows and shared, or for an update placements, new domains and new flows), checked against the project: unknown files and domain names, and files left without a home, come back as a tool error to fix. Should it still ask, inside a Map action what only reads goes ahead whatever the agent titles it (`only_reads`, by `PermissionRequest::kind`): a shell command that only reads (`read_only`), reading and searching, and exploring subagents (OpenCode's `explore`). The call (`AgentRun::proposed`, `Action::proposal_from_call`), else a fenced TOML reply (`Action::proposal`), shows as a proposal outlined in the agent's colour: Keep (⌘↩) saves it, Discard (or Esc) drops it, editing changes it, and a reply in the conversation redoes it; Jig applies an update itself, so only unsorted files are placed and confirmed domains never move. Editing by hand: double-click a domain's name or F2 renames it, its Rename and Purpose buttons edit in place, at Site, with tints on, dragging a file into another domain's region moves it, dropping a domain onto another merges them; edits save at once and ⌘Z / ⇧⌘Z undo and redo them. Saved in `.jig/map/domains.toml` (`[[domain]]` name, purpose, offers, why, members as paths, `folder/` or `path#Type`; `[[flow]]` from, to, label; `[shared]` members), committed. Once saved, each domain's colour tints its boxes at Site and Plan; the header's Domains switch turns that off. Copy as Markdown copies each domain's name, purpose and offers and the flows; Export Image (Copy Image, Save Image…) draws the level showing (Domain and Plan whole, Site as in view) as SVG, made a PNG with resvg (`view/export.rs`). `index_domains_live` (`JIG_MAP_ROOT`, `-- --ignored --nocapture`, after `cargo build`) runs Index Domains with the user's agent and counts what it asked; `grouping_live` (`-- --ignored --nocapture`, `JIG_MAP_PROJECT`) prints the grouping, and writes what Index Domains would ask to `JIG_INDEX_PROMPT` or reads an answer from `JIG_INDEX_REPLY`. **The agent on the Map** (`map/lens.rs`, `map/lens/`, `view/lens.rs`, `view/lens_draw.rs`, `view/ask.rs`, `workspace/map_agent.rs`): ⌘K there opens the input beside the boxes selected, and the conversation is told what's selected (names, places, purposes; at Plan, signatures and file:line; at Domain, the `domains.toml` entries) and a compact outline of the level (boxes, arrows, counts), never code (`MapView::question`). `Jig --map-mcp` (`map/lens/mcp.rs`, handed over by `jig_ai::map` beside the task tool: OpenCode's config and permissions, ACP's `session/new` and `session/load`) has `map_highlight`, `map_note`, `map_trace`, `map_tour`, `map_group`, `map_propose`, `map_describe` and `map_clear` (and the domains actions' `map_project` and `map_propose_domains`), each checked against the index: places are `path#Type.method`, `path#function`, `path` (any real file, Svelte too), `folder/` or `domain:Name`, and a name not found draws nothing and comes back with names like it (`lens::resolve`). The tools are allowed without asking (OpenCode's rules; over ACP Jig answers `session/request_permission` for them); they change no code. A drawing reaches the Map from the agent's own report of the call (`AgentEvent::Drew`, `Turn::Drew`), so it belongs to its conversation: a row in it (Show/Hide, Pin, Tour), gone when it closes, back when it's picked up. Every place lands on the box holding it at the level showing (`MapView::landing`: its function at Plan, else its type's or file's frame; at Site the box it's in as far as it's open; else its domain); a trace's steps in a row on one box fold into one stop listing its range, joined by one dashed path (`lens::fold`); boxes out of view get an arrow at the canvas edge that flies there; a list names each drawing and its steps, greying those the level can't show. Drawings never move the camera: ←/→ tour a trace (its Step through button, or → with one trace showing), the camera following across levels (`MapView::fly_to`), with a guide along the top (Back, the step, Next) and the step's words standing out while the rest fade; Esc ends it. The list of drawings sits top left, or top right when the conversation covers that corner; a link in the agent's answer flies the Map there (`Workspace::open_agent_link`, the code when the Map isn't showing). `map_describe`'s purposes and labels show dashed, as proposals: Tab or Enter keeps them (a domain's in `domains.toml`, the rest in `.jig/map/purposes.toml`, which Site's boxes read), Esc rejects them. `map_propose`'s ghosts sit beside the place they go by, with Make Task and Implement (asked in the conversation, every edit reviewed) and Dismiss. Pin saves a drawing to `.jig/map/pins/<title>.toml` (committed, by place names), shown on the Pinned layer (header switch); a pin whose places are gone is listed as orphaned. Explain (header, View > Explain This Level) is a Map action asking the agent to describe the level. Export Image draws the drawings too, with their list below. `map_agent_live` (`JIG_MAP_ROOT`, `JIG_MAP_FILE`, `JIG_MAP_ASK`, `JIG_PICTURES`, `-- --ignored --nocapture`, after `cargo build`) asks a real agent on a project's Map and saves pictures of the answer; `map_pictures_live` takes `JIG_MAP_DRAWING`, a JSON list of `{tool, input}`, to draw over every level. **Sketching** (`map/sketch.rs`, `view/sketch.rs`, `view/sketch_draw.rs`): the tool strip in the canvas's bottom left (pointer, box B, arrow A, note N, frame F; Esc goes back to the pointer, and each tool goes back to it after one shape) draws labelled boxes, labelled arrows, sticky notes and frames, in neutral ink, never the agent's orange; no free-hand ink. A shape's label is typed in place as it's drawn (double-click edits it, ⌫ deletes the selected shapes, a box with its arrows and notes), and shapes are selected and dragged like boxes. A sketch belongs to the level it was drawn at (`level` is `site`, `domain` or `plan:<place>`, the view's key); new shapes go in the sketch being drawn there, else a new "Untitled sketch" (its bar's title double-clicked renames it, and its file). Boxes, floating notes and frames are placed relative to the nearest real box (`near`, `at`: at Site its own box, so they don't move as boxes open) and move with it; an arrow dragged from or onto a real box is attached to it (`from`/`to` a place), and one let go on nothing makes a box there; a note clicked onto a box is on it (`on`) and moves with it. At other levels, a box carrying a sketch gets a ✎ mark (`sketch_marks`, by the places it names) that goes there (`MapView::go_to_sketch`). Saved as you draw in `.jig/map/sketches/<title>.toml` (committed: `title`, `level`, `task`, `archived`, `[[box]]` id, label, purpose, near, at, size; `[[arrow]]` from, to, label; `[[note]]`, `[[frame]]`), a box's id following its label; ⌘Z and ⇧⌘Z undo sketch edits before domain ones. ⌘K with sketch shapes selected (or the bar's title clicked, selecting it all) tells the agent the sketch as data (`MapView::sketch_lines`: each box named `sketch:<sketch>/<box>`, new or real, arrows, notes, frames, the selected ones marked, and the real places it's attached to) and that it's the user's: the agent never edits it, only answers beside it, with `map_note` on its boxes (places resolve `sketch:` names, `Place::Sketch`, landing on the box) or `map_propose` ghosts near them. Adopt (on a proposal, or on one ghost) makes ghosts boxes of the user's sketch where they're drawn, with their arrows (`MapView::adopt`). The bar above each sketch shows how many boxes are real and Make Task: a conversation (`MapEvent::Converse`) asking the agent to write a planner task from it for the user to agree to before `create_task`, its description ending with a link to the sketch file; a task linking a sketch becomes its `task` (`link_tasks`, on reading the tasks again), the bar then shows it (a click opens it in the planner, and the task's link opens the Map at the sketch) and Implement runs it in a conversation (`MapEvent::Implement`), every edit reviewed. As the project is read again, a box is matched by its label (`sketch::match_box`: letters and digits, case ignored, against types, functions and file names; several in one file are one thing, several elsewhere narrowed to those by the box's `near`, else unsure and left sketched with a "?") and drawn solid with ✓ and its place; an arrow between real ends is drawn solid once the code calls along it either way. Once every box is real and its task (if any) is done, the bar offers Archive: off the canvas, still in the header's Sketches list (restore, delete). Export Image draws sketches too. `sketch_pictures_live` (`JIG_MAP_ROOT`, `JIG_MAP_FILE`, `JIG_SKETCH`, `JIG_PICTURES`, optional `JIG_MAP_DRAWING`, `-- --ignored --nocapture`) puts a sketch file in a project for a moment and pictures it, the agent's answer, and the level above. `sketch_agent_live` (`JIG_MAP_ROOT`, `JIG_MAP_FILE`, `JIG_SKETCH`, `JIG_MAP_ASK`, `JIG_PICTURES`, `-- --ignored --nocapture`, after `cargo build`) asks the user's agent about a sketch, then has it make a task of it and agrees, allowing only what reads, and takes the sketch and task out after.

Typed text is a message for the agent. `/` lists the agent's commands and skills (OpenCode's from `GET /command`, an ACP agent's from `available_commands_update`; text after the name is its arguments, run with `POST /session/:id/command` in a new conversation).

### The input

- ⌘K, the Agent button in the title bar (a toggle: pressed while the input is open, glowing briefly as it opens, and it or ⌘K again closes it; the input itself opens with the floating panels' short fade in the window's right half, its top where the conversation's will be, `Workspace::right_centre`; notes open at the cursor), or the sparkle button that appears just right of a selection while the code has focus (`workspace/selection_button.rs`; hidden while a note, an edit under review or a panel is open, and turned off with Settings > Editor > Agent button on selections). Right-click > Ask the Agent… and Edit > Ask the Agent… open it too. Send to Agent (⇧⌘L, Right-click and the Edit menu; `Workspace::send_selection_to_agent`) puts the selection, or the cursor's line, in the open conversation's reply box as a chip (`@src/a.rs:10-12`, an inline token), or opens a new conversation empty with it; the reply is sent with the code its chips name (`jig_ai::agent::message`).
- The typed text is listed first under **Message**, the earlier conversations it matches below. Enter on the message starts a conversation about the selection, or the cursor's line when nothing is selected (`Workspace::start_conversation`, `commands::Ask`); the agent is told the file, the lines and their text (`jig_ai::agent::Prompt`). The text wraps, the input growing to eight lines, and Shift-Enter starts a new line. After `/`, when the text is how the highlighted command's name starts, the rest of the name shows in grey after it, and → or End at the end of the text completes it.
- The footer says what will happen. At its end a chip shows the agent and its model; clicking it or ⌥M lists the agents in place of the conversations, Enter shows that one's models and ⌫ goes back (with only one, its models at once; typing a model's name lists matches from all of them), and Enter on a model picks it for the window (`Workspace::pick_model`, `AgentState::pick`; a conversation keeps the agent and model it started with). Settings keeps the defaults; changing them there drops the window's pick. ACP agents are put on their model with `session/set_config_option` as a conversation starts or is picked up.

### Review

An edit goes into its file's buffer provisionally: highlighted, file read-only, one undo step. The agent's new text is diffed line by line against the file (`jig-app/src/diff.rs`): only lines that differ are edited, only new lines are highlighted, and only lines actually removed are listed. Tab/Enter accepts, Esc or ⌘Z rejects.

Providers' config (`config.rs`), and `agent.rs` (the types shared by every agent, the first message of a conversation, `Prompt`, and the unified-diff applier) with, under `agent/`, `opencode.rs` (OpenCode client), `acp.rs` (Agent Client Protocol client) and `harness.rs` (either one behind `Backend`/`Session`). `config_file.rs` edits `config.toml` keeping comments and holds the major-provider templates; `keys.rs` stores keys typed in Settings; `models.rs` lists a provider's models (chat models only, `http.rs`); `agent::opencode::Target` hands the agent's provider to OpenCode as `OPENCODE_CONFIG_CONTENT`, named `jig-<provider>`. Jig itself never calls a model.
- Providers in the app: `providers.rs` holds the config, keys and each provider's model list as a global that workspaces observe. Settings is split by what each choice is for: Providers connects the major providers (paste a key, or switch on a local server); with Refresh Models, whose lists show whether each key works; Agent picks the agent, its model (OpenCode's from the providers, an ACP agent's from the models it offers, remembered from its last run in the agents folder's `models.json`, kept in `[agent] models`) and its permissions. `agent.rs` restarts the shared OpenCode server when the agent's provider config changes; runs underway keep the old one.
- `assets/`: built-in agents (`default-agents.toml`), formatters (`default-formatters.toml`), snippets (`default-snippets.toml`), Ember themes, file icons, the app icon and logo (`app-icon/`: `Jig-iOS-Default-1024@1x.png` is the icon (from Icon Composer), `jig-mark.svg` and `jig-mark-dark.svg` the logo, `social-preview.svg` GitHub's preview image; `render.sh` makes the PNGs and the `Jig.icns` that `script/bundle-macos.sh` bundles).

Per project: `.jig/run.toml` (run configurations), `.jig/tasks/` (the task planner's tasks), `.jig/map/domains.toml` (the Map's domains, committed), `.jig/map/sketches/` (the user's sketches, committed), `.jig/map/pins/` (pinned drawings, committed), `.jig/map/purposes.toml` (purposes and labels kept from the agent, committed) and `.jig/map/places.json` (how each Map view is arranged, kept out of git). User files live in `~/.config/jig/`: `debuggers.toml` (own debuggers; same key replaces a built-in), `agents.toml` (own agents; same key replaces a built-in), `language-servers.toml` (own language servers, `[[server]]`; same name replaces a built-in, and yours come first; read at startup), `formatters.toml` (own formatters; same key replaces a built-in, and yours come first), `config.toml` (providers, and the agent's model as `agent = "provider/model"`; an older `agent_model` still reads; Jig mode's retired `quick` is ignored and dropped when Settings writes the file), `keys.toml` (API keys, only where there's no system keychain), `settings.toml` (changed shortcuts under `[shortcuts]`, what saving does under `[formatting]`, the agent's permissions under `[agent]`), `snippets.toml` (own snippets; same name replaces a built-in), `recent.toml` (projects for the home page), `sessions.toml` (each project's open files and showing tab, saved as tabs change and reopened when its folder opens on an empty window; `session.rs`, `workspace/session.rs`).

## Providers

- No provider by default: Jig favours no vendor. The built-in `config.toml` connects none and picks no model (`agent = ""`, read as none), so a conversation on OpenCode says to connect one in Settings > Providers (other agents bring their own sign-in and models). The first provider connected starts the agent on one of its fast models once it lists them (`ProviderTemplate::fast`, e.g. Haiku, mini, flash; a local server's first model), never over a model already picked (`providers::start_on_a_model`). OpenCode Go is one provider among the others (Anthropic format, an `x-opencode-session` header). API keys never go in `config.toml`: one typed in Settings goes in the system keychain (macOS Keychain, Windows Credential Manager; elsewhere a 0600 `keys.toml`) and wins over the `api_key_env` variable.

## Working on Jig

```sh
cargo run -p jig-app -- <file-or-folder>
cargo test                       # ~600 tests, including headless UI tests
cargo clippy --all-targets       # keep at zero warnings
cargo fmt
cargo deny check                 # advisories, licences, sources (deny.toml); CI runs it
script/bundle-macos.sh           # builds target/Jig.app
```

- Live tests and tools that call real agents and models are opt-in: `cargo test -p jig-app agent_live -- --ignored` (needs OpenCode), `JIG_SERVERS_DIR=<scratch> cargo test -p jig-app server_install_live -- --ignored` (installs YAML's server with npm), `cargo run -p jig-ai --example agent -- <dir> "<prompt>" [<ACP agent command>…]`. They cost money; don't run them in loops.
- Depend on `gpui-kit` only, pinned exactly (`=0.7.0`). GPUI distributions can't be mixed.
- Capabilities: `architecture.toml` groups jig-app's top-level modules into capabilities, each reached by others only through its `contract` and only if they list it in `uses`, and says which Jig crates each crate may depend on. `crates/jig-app/tests/architecture.rs` checks this from the source's tokens; crossings that break it today are in `architecture-baseline.txt`, which may only shrink (`JIG_ARCH_BLESS=1 cargo test -p jig-app --test architecture` rewrites it). A capability may have a crate of its own (`crate = "jig-map"`), whose privacy the compiler enforces; the test then checks only `uses`. The language tooling is layered, each layer a capability of its own: `tools` (where Jig's tools live: the PATH, its data and config folders, installers) ← `languages` (the languages and servers as data, and finding a server's program) ← `formatters` and `debuggers` ← `language_servers` (`lsp` and `definitions`). A new top-level module goes in a capability.
- UI tests live in `workspace/tests/`, one file per feature, with the shared helpers in `workspace/tests.rs`. They open a real window on GPUI's test platform: `open(cx, path)`, then `step(cx, window, |window, cx| …)` to press keys and let effects settle. Type and press in separate steps when the list needs to refilter in between.
- Match the surrounding style: doc comments say why, in plain sentences; names over comments; small focused functions. User-facing text is short, plain and specific ("Save the file first, so the agent knows which project it's in.").
- Cross-platform: GPUI runs on macOS, Linux and Windows, and CI builds all three. Keep macOS-only touches behind `cfg!(target_os = "macos")` with a plain fallback, bind keys with `secondary-` (⌘ on macOS, Ctrl elsewhere), gate Unix APIs (`std::os::unix`, `libc`) with `#[cfg(unix)]`, start every other program with `.no_window()` (`jig_process::NoWindow`; release builds are windowed on Windows, so a console program would otherwise flash a window of its own), and one that could hang (an installer, git over the network) with `jig_process::output_within`, which stops it and what it started after a limit, and put caches and config where each OS expects them.
- New languages: enable the grammar feature in the root `Cargo.toml`, or, for a grammar GPUI Kit has no feature for, add its crate to `jig-app`'s `Cargo.toml` and a line to `languages/grammars.rs` (its own highlights, or the `.scm` file its crate ships copied into `languages/queries/`; older Neovim capture names are mapped onto the theme's). The crate must build on `tree-sitter-language` or `tree-sitter >= 0.21`, never pull in a second tree-sitter, and resolve beside GPUI Kit's pins; check what it adds to the release binary, since some parse tables are 5-15 MB. Then add it, and a server and formatter if there are any, to `assets/default-languages.toml` (`starter = true` puts it in everyone's list from the start; otherwise it's added from the Library). Users can't load grammars of their own.
- When a feature lands or changes, update this file if it changes the concept or the layout.
