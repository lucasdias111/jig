# AGENTS.md

Jig is a macOS-first code editor (it also builds on Linux and Windows) where AI works through a coding agent called up at the cursor, not through a chat or an IDE somewhere else. You select code, press ⌘K and say what you want; the agent works in a small conversation beside the code, and each edit it wants shows inline for you to accept or reject. The agent reads this file, so keep it short and current.

## The concept

**AI as a tool, not a colleague.** IDE refactorings are precise but fixed; agents are open-ended but take you away from the code. Jig keeps the refactoring interaction, anchored to the code you point at and reviewed edit by edit, with an agent behind it. The name is from woodworking: a jig guides precise, repeatable cuts by hand; Jig is that guide for the agent. All AI goes through the agent: there are no one-shot model calls and no saved prompts of Jig's own for the user to pick (an agent's own commands and skills, called "agent commands", stand in for those). The one exception is the Map's actions (Index Domains, Update Domains, splitting a domain): Jig-written instructions, each starting a normal, visible conversation; there's no user-editable prompt library.

Principles:

- **Near the code.** Every interaction is anchored to the cursor. No side panels, except an agent conversation you pin to the side yourself.
- **You decide.** Every change is previewed and needs an explicit accept. Nothing reaches the disk unreviewed (unless you accept the rest of an agent conversation's edits with ⌘↩), and the agent's shell commands, web access and subagents wait for a go-ahead too.
- **Keyboard first.** Few shortcuts, each obvious.
- **Clean and Mac-like.** The code is the interface. Restrained colour, floating panels, follows system light/dark.

### The agent

The input (⌘K) starts or picks up a conversation with the agent. The agent has its own colour (theme info, orange) and icon (bot) everywhere it appears: input, highlight, buttons, conversation tag.

- **Agents.** A coding-agent harness at the code, agnostic about the agent: Settings > Agent picks it from the agents listed as data (`agents.rs`; `assets/default-agents.toml` has OpenCode, Claude Code, Codex and Gemini CLI and documents every field; the user's `agents.toml` adds any agent that speaks the Agent Client Protocol, or replaces one by `key`; Install runs its `install` into Jig's agents folder, whose `node_modules/.bin` and `bin` are searched with the PATH; `[agent] use` in `settings.toml`). OpenCode (`kind = "opencode"`, the default) runs through Jig's own client (`opencode serve`, `jig-ai/src/agent/opencode.rs`), with the model picked under it on the Agent page (other agents bring their own model and sign-in, which the page says), edits always set to ask and questions with choices. Every other agent runs over ACP (`jig-ai/src/agent/acp.rs`): one process per agent, JSON-RPC on stdio, Jig as a client that reads files from disk and writes them only after review (`fs/write_text_file`; an edit already allowed by permission is written without asking twice). An agent that answers "Authentication required" (`acp::SignInNeeded`) gets its sign-in methods offered in the conversation: a `terminal` one opens the system terminal with the agent's own login (`agent::open_in_terminal`, a `.command` file on macOS), then Enter tries again; any other is `authenticate`d, and the turn is sent again. `jig-ai/src/agent/harness.rs` puts both behind one `Backend`/`Session`, and `jig-ai/src/agent.rs` holds the types every agent shares. The agent reads and edits the whole project with its own skills, commands and instructions file. Each edit it asks about (OpenCode's diff; ACP's permission request with a `diff` or the tool's old and new text; or a file it hands Jig to write) arrives *before* it's written and opens in its file's tab as a normal preview. An ACP agent set to edit without asking can't be stopped; the transcript says "Edited x without asking". The built-ins are set up to ask: Claude Code's default mode does, Codex starts `read-only`. Enter/Tab accepts (OpenCode writes it), Esc/⌘Z rejects (the agent is told and may retry). ⌘↩ accepts it and the rest of the conversation's edits (`AgentRun::accept_edits`): each is then written without opening its tab and listed as edited, except in a file with unsaved changes, which the agent is told to leave alone, as before. The conversation is `Workspace::chat`; a short note (`Workspace::note`, such as why nothing can run) shows apart from it, and Esc dismisses the note first. While it's docked, ⌘K still opens the input at the code, for another conversation or an earlier one. Starting another conversation replaces the one on screen, undoing an edit of its still under review. A conversation belongs to the project, not the file it started from: it works in the folder open in the sidebar (or the file's repository when there's none, `Workspace::agent_project`), its header names that project, and it stays open and working across tab switches; an edit it proposed waits in its file's tab (Esc or clicking the file in the conversation goes back to it, and accepting it settles it there). A saved file isn't needed once a folder is open. The run is a floating conversation at the code (`jig-commands/src/chat.rs`): what was asked, the agent's replies, each edit taken or rejected, and a reply box once the agent answers. It opens to the right of the code it's about when the window has room, below the cursor otherwise. Its header shows the model it runs on: clicking it lists the agent's models (OpenCode's from the providers, an ACP agent's own) and picks one for the rest of the conversation, an ACP agent switched at once with `session/set_config_option`; a conversation keeps the agent it started with. Drag it by its header to move it (it then stays put) or by its corner to resize it; its pin button docks it to the window's right edge, full height, beside the code, on the editor's own background; docked, its left edge drags to resize it, and the next conversation opens docked at that width until it's unpinned. Replies render Markdown. The transcript has a scrollbar and keeps to its end while scrolled there (a long reply's Markdown is laid out a frame late, `chat::follow_the_end`); scrolled up, it stays put and shows a More below button. A reply continues the same OpenCode session, and a reply like `/review main` runs that OpenCode command in it. Shell commands, web fetches and searches, and subagents (`task`) ask by default; Settings > Agent (`settings_window/agent_page.rs`, `[agent]` in `settings.toml`, `jig_ai::agent::Permissions`) sets each to ask, allow or don't allow, and turns the question tool off. The rules are re-sent to OpenCode at the start of every turn, so a change applies from the next one, earlier conversations included; edits always ask and outside the project is always denied. Asked, the conversation shows what it wants to run with three buttons: Allow (Enter/Tab, once), Always allow (⌘↩; OpenCode's `always` reply, naming the patterns it will remember, or an ACP agent's `allow_always` option; an agent with neither has Jig allow that kind of request for the rest of the conversation) and Deny (Esc). What ran is listed in the transcript either way; two or more calls in a row fold into one "Used N tools" row that a click opens (`chat::transcript_rows`), while an edit made without asking always shows. Over ACP, the settings map onto tool kinds (`execute` is shell, `fetch` the web, reading and searching need no go-ahead, anything else asks). With OpenCode's question tool on (the default): the question shows with numbered options, answered by clicking one or typing a number or your own words in the reply box (Esc declines). Edits and requests from its subagents come through the same way. Each subagent has a row of its own in the transcript (`ChatEntry::Subagent`: what it was given, how many tools it used, a spinner while it works), which a click opens to what it did, reading included, and the report it gave back; its words don't go into the agent's reply. Subagents are told apart by the session each runs in: OpenCode's child sessions (the `task` tool's `sessionId`, its output the report), and over ACP the draft's subagent sessions (Jig declares `clientCapabilities.subagents`; `subagent_spawned` and `subagent_state_update` on the conversation's session, the subagent's own updates and requests on its own, handed to the conversation's listener, `Connection::subagents`). An ACP agent without them shows its subagents' work as its own. Nothing outside the project. Esc in the code, once a completion list or snippet is closed, rejects an edit under review there, else stops the agent's turn; Esc again closes the conversation. From the Files, Git or Tasks view, Esc goes back to the code and closes the conversation only if it's idle (`Workspace::leave_sidebar`). Edits the agent asks for at once are shown one after another. Each edit's row in the transcript counts the lines it added and removed, and a click opens its diff (`diff::edit_lines`). 15-60 s.
- **Earlier conversations.** Every conversation stays with its agent. OpenCode's are titled with what was first asked (`metadata.jig`; older Jig sessions are known by their edit-asks rule, and the user's own OpenCode sessions aren't listed). An ACP agent's come from `session/list` with its own titles, and are picked up with `session/load`, as far as the agent can; its `/` commands are the ones it last announced (`available_commands_update`), so they show once a conversation with it has started. The input lists them under **Conversations**, latest first, filtered by the typed words; Enter on one picks it up with its transcript (`Backend::open`, `history` reads it back). ⌥⌘K (Agent Conversations…, in the Edit menu and Settings > Keyboard) and the conversation's history button open the input.
- **Tasks.** A task planner in the sidebar (⌃⇧T, `planner.rs`, `workspace/planner.rs`): tasks with a title, a Markdown description and a todo list, one file each in the project's `.jig/tasks/<id>.md` (`# Title`, the description, `## Todo` with `- [ ]` items; `jig-ai/src/tasks.rs`). Each is a card: click it to fold it open, check todos off or add one under it; hovering its header shows Edit and Move to Trash, open or not. + or View > New Task… and Edit open the form as a sheet over the window (`planner/form.rs`); typing `@` in its description or a todo lists the project's declarations and files (`planner/symbols.rs`, found by the shapes declarations take, so it works without a language server; with nothing typed, the open file's names), and picking one puts in its link. Hovering a todo shows an Agent button that delegates that step (`Workspace::delegate_todo`): it starts a conversation as a typed message would, with the whole task as context (`Task::step_context`, the step marked). The code the step links to is opened first and is what the conversation is about, else the selection; the agent checks the step off with `update_task` when done. A card's hover actions also hand the whole task to the agent (`Workspace::implement_task`, `Task::context`), to work through its open todos in order, checking each off. Agents make them through a tool: `Jig --tasks-mcp` is a stdio MCP server (`tasks/mcp.rs`) with `create_task`, `list_tasks` and `update_task`, handed to OpenCode in its config (started in the project's folder; its tools are `jig_*`) and to ACP agents in `session/new` and `session/load` with `--project`. Its instructions and Jig's system prompt tell the agent to write plans as numbered lists, to ask whether to save one as a task whenever it proposes three or more steps or work across several files, to save it only once the user agrees, to keep a task short (a summary, then `### Background`, `### Context`, `### Purpose` and `### Risks`, a sentence or two each, then the todos), and to link every code reference as ``[`name`](path#L12)``. Settings > Agent's Tasks row (`Permissions::tasks`, Allow by default, since the agent asks in the conversation) decides whether saving and updating tasks also waits for Allow; over ACP the tool is known by its title (`mcp__jig__create_task`). The folder is watched (just `.jig/tasks` and its parents), so a task an agent makes appears at once, opened, with a dot on the Tasks button while the view is hidden. Clicking a link opens the file at the name nearest the line (`planner/links.rs`), so links survive edits; web links open in the browser. Go Back and Go Forward (⌃- and ⌃⇧-, Alt-arrows off macOS, or a mouse's back and forward buttons; `workspace/navigation.rs`) return across jumps: task links, Go to Definition, Go to Line, problems and Find in Files results.

- **The Map.** One canvas you zoom out to from anywhere in the code, for understanding and deciding: it never changes code (`map.rs`, `map/`). Levels: **Code** (the editor) → **Plan** → **Site** → **Domain**. ⌘B (View > Show Map, or the title bar's Map button left of the Agent button, which reads Code while the Map shows) or a pinch-out in the code (`Workspace::pinch_code`) shows it in place of the code (`workspace/map.rs`; one `MapView` per workspace, on the project the file's in: the sidebar's folder, else the nearest folder with `.git` or a manifest, `index::root_of`), flown out of the function at the cursor to its Plan with that box selected (you are here). **Plan** (`map/plan.rs`, laid out by `map/layout.rs`) is a neighbourhood around a focus, never the whole project: a function's callers left and callees right, one hop, at most 8 a side before "+N more", a side's tests folded into one box, packages outside one box each, hubs as badges, further hops opened by a box's ◀ N and N ▶ buttons; or a module's (a folder `dir/`, a file, or `path#Type`, entered from Site) functions framed by type, called ones right of their callers, with calls in and out at the edges. A box shows the function's name and compact signature (`plan::signature`); resting on it peeks at its code. Calls are arrows, dashed when only a guess by name, solid when the index or the language server (`callHierarchy`, asked about the focus, `MapEvent::AskServer`) is sure. Entering another function re-centres: its box stays put, the others glide, new ones fade in and those out of range fade where they were. **Site** (`map/site.rs`) is Domain zoomed into: the same regions in the same places (Domain takes their rects from Site, `DomainLevel::of`), each holding only its own share of the code (`Site::of` over the domains showing, so before Index Domains over Jig's drafts): its components (the deepest folder with a manifest, else the top folder), then their modules and folders, then files, and a file's types only where several have functions. A component in several domains shows in each with its own slice (`backend › bookings` in Bookings, the frontend's booking routes beside it). Folders that only lead somewhere fold away: a chain of single folders, `src`, `main`, `java` (`BOILERPLATE`), a component holding one folder (`balladeby-backend › bookings`), a folder holding one file; a Java file is its type's box. Laid out once, every box at the size its contents take (a file as wide as its title), so opening one only shows what's inside: a box starts opening at `Node::open_at`, once it's wide enough on screen and a typical box inside would read (or by 700 px), what's inside fading in (`view/scene.rs`, `site_scene`). A closed box shows its title (two lines), its purpose from its README or doc comment (`outline::file_purpose`, `index::readme_purpose`) or else what's inside by name, and how much it holds; a frame's title fits its bar. Arrows join only boxes side by side (`Site::arrows`: each call drawn between the two siblings holding its ends, summed, thicker with more, the count on it and the calls on hover); calls leaving an open region end at its edge as a stub naming the domain at the other end (`Stub`, "to Payments · 3 calls", and "from …" for calls coming in), and between regions still closed the domains' flows show as at Domain. Tests (`site::is_test`) and calls into and out of Shared are left out until the header's Tests and Shared switches show them (`Show`). Files the index can't read (Svelte, templates, other languages, `OTHER_SOURCES`) are placed like the rest. **Moving** (`map/view/zoom.rs`): pinch or ⌘-scroll zooms within a level; past a threshold it cross-fades to the next (`Transition::cross_fade`: the old level drawn fading out as the new one fades in, the box entered growing into its contents, or what's left shrinking into the box holding it), and a gesture that crossed zooms no further until it's let go. Zooming out of Plan goes to Site, onto the folder holding where you were with that box selected and its neighbours in view (`camera_on_site_box`, no closer than natural size), inside the domain holding it; Domain and Site are one zoom: zooming into a region far enough that it opens is Site, and zooming out of Site until no region in view is open is Domain, the region in the middle selected, the view staying put both ways (`MapView::continuous`); zooming in at Site over a file or type goes to its Plan, over a Plan's function to its Plan, and over the Plan's own function into its code. ⌘↑ and ⌘↓ step a level the same way, Enter or a double click enters the selected box (a region or folder flies in until it fills the view, open), the header's Code · Plan · Site · Domain switch does too, Esc clears the selection and then goes back to the code, and anything that focuses the code shows it again. Dragging moves a Plan's boxes (Site's stay where the project puts them), right or middle drag pans, and Tidy lays a Plan out afresh. Entering the Map, each level stepped into and each re-centring is a place for Go Back (`navigation::Place::Map`); zooming within a level isn't. Each view keeps its dragged places, opened hops and viewport in `.jig/map/places.json`, which Jig adds to `.jig/.gitignore`. Files, Go to File and the sidebar open code; the Map is a zoom away. **Index** (`map/index.rs`, `map/outline.rs`): every Rust, JavaScript, TypeScript (and TSX), Python, Go, Java, C, C++, Swift and Zig file outlined with tree-sitter on a background thread (functions with contracts and calls, types, imports, purposes; `outline/syntax.rs` lists functions, and each language's `Syntax` in `outline/lang/<lang>.rs` says how it lists them and which of its nodes are calls), calls resolved by name, narrowed by declared types, imports and owners; read again file by file, keeping what unchanged files read as (`Project::read_again`). `big_project_live` (`JIG_MAP_PROJECT=<repo>`, `--release -- --ignored --nocapture`) checks that reading, laying out Site and a frame stay within budget on ~10k files; `map_of_jig_live` (`-- --ignored`) draws the Map of Jig itself, and `map_pictures_live` (`JIG_MAP_ROOT`, `JIG_MAP_FILE`, `JIG_MAP_AT`, `JIG_PICTURES`, `-- --ignored --nocapture`) renders a project's Plan, Site and Domain at stepped zooms and a zoom from Domain down into the Plan as PNGs, with Export Image's drawing, to check the design without a screen. **Debugger** on Plan (`map/debug.rs`): paused, the function and its callers down the stack light up as a path, and a pause in a function not on the Plan shows its Plan (`Workspace::refresh_map_debug` hands over the frames); running, each function on the Plan gets a logpoint on its first statement (`logMessage` in `setBreakpoints`, `jig-fired <id>`, kept out of the console; `workspace/live.rs`), so it glows as it's entered and the call it came along lights with a pulse; the header's Live switch turns that off. Stepping happens in the code. **Domain** (`map/domains.rs`, `map/domains/`, `view/domain.rs`, `view/domain_draw.rs`): the project as business areas, each a big region in its own colour, sized by what it holds at Site, with only its name, full purpose and offers (`domains/level.rs`; zooming in, ⌘↓ or Enter goes to Site there); one labelled link per pair of domains; Shared and Unsorted greyer, apart below. Every file has one home: whichever domain or Shared names it most closely (`path#Type` over its file over its folders, deeper first, `Domains::home_of`), else it's Unsorted. Before any domains are saved it shows Jig's own grouping as dashed drafts (`domains/grouping.rs`: top folders, opened while fewer than three and wherever one holds most of the code, loose files joining the folder of their name or the group they call most, labelled by their functions' commonest words, each group's two strongest call links as flows) under a banner: "Index Domains to name and describe these". **Index Domains** (banner, header, View menu) and **Update Domains** (header, View menu, when files are Unsorted), and Split… on a selected domain, start a normal conversation (`MapEvent::Ask`, `Workspace::start_map_action`, `AgentRun::map_action`; instructions in `domains/actions.rs`): Index hands over the grouping with every source file, the index's unread ones too, and asks for plain offers, no routes; Update lists only the unsorted files with the saved domains; commands that only read run without asking (`read_only_command`). The answer's TOML (`Action::proposal`) shows as a proposal outlined in the agent's colour: Keep (⌘↩) saves it, Discard (or Esc) drops it, editing changes it, and a reply in the conversation redoes it; Jig applies an update itself, so only unsorted files are placed and confirmed domains never move. Editing by hand: double-click a domain's name or F2 renames it, its Rename and Purpose buttons edit in place, at Site, with tints on, dragging a file into another domain's region moves it, dropping a domain onto another merges them; edits save at once and ⌘Z / ⇧⌘Z undo and redo them. Saved in `.jig/map/domains.toml` (`[[domain]]` name, purpose, offers, why, members as paths, `folder/` or `path#Type`; `[[flow]]` from, to, label; `[shared]` members), committed. Once saved, each domain's colour tints its boxes at Site and Plan; the header's Domains switch turns that off. Copy as Markdown copies each domain's name, purpose and offers and the flows; Export Image (Copy Image, Save Image…) draws the level showing (Domain and Plan whole, Site as in view) as SVG, made a PNG with resvg (`view/export.rs`). `grouping_live` (`-- --ignored --nocapture`, `JIG_MAP_PROJECT`) prints the grouping, and writes what Index Domains would ask to `JIG_INDEX_PROMPT` or reads an answer from `JIG_INDEX_REPLY`.

Typed text is a message for the agent. `/` lists the agent's commands and skills (OpenCode's from `GET /command`, an ACP agent's from `available_commands_update`; text after the name is its arguments, run with `POST /session/:id/command` in a new conversation).

### The input

- ⌘K, the Agent button in the title bar (a toggle: pressed while the input is open, glowing briefly as it opens, and it or ⌘K again closes it; the input itself opens with the floating panels' short fade just right of the selection, or the cursor's line, so it covers no code, and below the cursor when the window has no room there; notes sit beside the code the same way, `Workspace::beside_anchor`), or the sparkle button that appears just right of a selection while the code has focus (`workspace/selection_button.rs`; hidden while a note, an edit under review or a panel is open, and turned off with Settings > Editor > Agent button on selections). Right-click > Ask the Agent… and Edit > Ask the Agent… open it too.
- The typed text is listed first under **Message**, the earlier conversations it matches below. Enter on the message starts a conversation about the selection, or the cursor's line when nothing is selected (`Workspace::start_conversation`, `commands::Ask`); the agent is told the file, the lines and their text (`jig_ai::agent::Prompt`). The text wraps, the input growing to eight lines, and Shift-Enter starts a new line. After `/`, when the text is how the highlighted command's name starts, the rest of the name shows in grey after it, and → or End at the end of the text completes it.
- The footer says what will happen. At its end a chip shows the agent and its model; clicking it or ⌥M lists the agents in place of the conversations, Enter shows that one's models and ⌫ goes back (with only one, its models at once; typing a model's name lists matches from all of them), and Enter on a model picks it for the window (`Workspace::pick_model`, `AgentState::pick`; a conversation keeps the agent and model it started with). Settings keeps the defaults; changing them there drops the window's pick. ACP agents are put on their model with `session/set_config_option` as a conversation starts or is picked up.

### Review

An edit goes into its file's buffer provisionally: highlighted, file read-only, one undo step. The agent's new text is diffed line by line against the file (`jig-app/src/diff.rs`): only lines that differ are edited, only new lines are highlighted, and only lines actually removed are listed. Tab/Enter accepts, Esc or ⌘Z rejects.

## Layout

Rust workspace, edition 2024, toolchain pinned in `rust-toolchain.toml`.

- `crates/jig-app`: the binary (`Jig`). Window, workspace, tabs, file tree (`file_tree.rs`; right-click for New File/Folder, Rename (F2), Move to Trash (⌘⌫), Copy Path and Reveal; ⌘-click, Shift-click, Shift-arrows and ⌘A select several, which Trash, Copy Path and dragging act on together; dragging rows onto a folder moves them into it, onto a file beside it, below the rows to the project folder, checked first so a taken name moves nothing; open tabs follow a rename or move and close when their file is trashed, unless unsaved), Go to File (⌘P), Find (⌘F) and Find and Replace (⌥⌘F) in the file (`find_panel.rs`, a floating panel over the editor's search engine, which is built `searchable(false)`; it starts from a short one-line selection and won't replace while a change is under review), Find in Files (⇧⌘F), menus, settings window, themes. Settings (⌘,, `settings_window.rs`) is laid out like a Mac app's: a sidebar of pages (Appearance, Editor, Languages, Keyboard, Updates; Providers and Agent under AI) with a search field, each page titled cards of rows; Theme Colors and each language open a page of their own with a back button. Languages works like Neovim's Mason: it lists the added languages (`[languages] added`; the starters in `assets/default-languages.toml` to begin with), and its Language Library page lists every bundled language with the tools it comes with, to add or remove (files in a language not added open as plain text). Each language's page shows its language server, its formatters (which one it uses, `[formatting] use`, ahead of its server) and its debugger, each with Install and Uninstall (`tools.rs` runs every installer, with `${os}` and `${arch}`, into Jig's `servers`, `formatters` and `debuggers` folders), and the files that add your own tools are at the foot of the list. Pages describe their rows as data (`settings_window/ui.rs`), so search covers every page and only the page showing is drawn. `JIG_SNAPSHOTS=<folder> cargo run -p jig-app --features snapshots` renders every page to PNG, light and dark, with GPUI's Metal renderer, for checking the design without a screen. `workspace/file_watch.rs` watches the folders of open files and shows changes made outside Jig in tabs without unsaved changes, as one undo step keeping the cursor (also checked when the window comes forward). `workspace/commands.rs` opens the ⌘K input, starts conversations from it, shows notes and routes the review keys; `workspace/agent.rs` runs the agent: conversations, their edits and requests, and picking up earlier ones; `agent.rs` owns the shared OpenCode server; `project.rs` finds the project root and `AGENTS.md`; `diff.rs` is the preview diff. `lsp.rs` runs language servers (not bundled; one that isn't installed is skipped, and one that stops before it has started, as a rustup proxy with no rust-analyzer for the project's toolchain does, says why in the status bar with the last line of its stderr, `lsp::Failures`); one started in a folder before its marker existed, as before `cargo init`, which rust-analyzer would never notice, is started again once the marker appears, checked on save and when the window comes forward, `lsp::is_current`). `assets/default-languages.toml` (read by `languages.rs`) lists every language (extensions, whole `filenames` such as `Makefile`, comment marker, LSP id, whether it starts in the list) and the servers serving them (commands, root markers, an `install` command and help); the user's `language-servers.toml` replaces a server by `name` or adds one, theirs first, read at startup. `lsp/install.rs` runs a server's `install` in its own folder in Jig's servers folder (beside the debuggers folder; `JIG_SERVERS_DIR` says otherwise), whose `bin` and `node_modules/.bin` are searched after the PATH; Uninstall moves that folder to the Trash, and open tabs connect to a newly installed server (`lsp::ServersChanged`) for ⌘-click go to definition and autocomplete, with `definitions.rs` guessing declarations and `completions.rs` offering words from the file when no server answers. Problems servers report (`publishDiagnostics`, `lsp/diagnostics.rs`) are kept per file, open or not, under the file's real path as a URI (servers write URIs their own way, e.g. `file:///c%3A/…`), with reports about text that has since changed dropped; `workspace/diagnostics.rs` shows them: squiggles in the theme's status colours, the message in a small panel on hover, error and warning counts in the status bar (click to step), and Next/Previous Problem (⌥F8/⇧⌥F8). They move with edits until the server reports again (a vendored-editor patch). Quick Fix (⌘., Edit menu, right-click; `workspace/quick_fix.rs`) lists, in GPUI Kit's code action list under the cursor, the server's quick fixes for the problems on the cursor's line (`textDocument/codeAction` with the problems as reported, only those carrying their edits, made as rename's are), then Fix with Agent (a conversation given the problems, for fixes the server doesn't have, including ones beyond the line, such as a missing dependency). A problem's panel, and the hover showing one, offer the same under the message (`PanelFixes`); both stay a moment after the pointer leaves, and while it's over them, so it can reach them. No server, nothing shown. `workspace/hover.rs` (parsing in `hover.rs`): resting the pointer on a name for 500 ms, or ⌘I (Show Hover) at the cursor, asks `textDocument/hover` and shows the Markdown in a panel below it (code blocks highlighted), with any problem there above it; typing hides it, as do Esc and the cursor moving. Typing `(` or `,` in a call asks `textDocument/signatureHelp` and shows the signature above the cursor, the active parameter in bold, until `)`, Esc or the cursor leaves the call. The editor draws neither (a vendored-editor patch: Jig draws the hover, sets its delay and hears what's typed), and neither shows while the palette or a review is open; both draw over notes and the agent's conversation. Right-clicking the code (`workspace/code_menu.rs`) offers Go to Definition, Find All References (⇧F12), Rename Symbol (F2), Quick Fix…, Ask the Agent…, the clipboard and Toggle Line Comment (⌘', or ⌘/). Rename (`workspace/rename.rs`, field in `field_box.rs`) asks the server for `textDocument/rename` and makes its edits in each file's buffer, opening tabs behind the current one for files that aren't open, unsaved and one undo step per file; without a server it renames whole-word uses in the file. Format Document (⇧⌥F, Edit menu, right-click; `workspace/format.rs`) asks the server for `textDocument/formatting`, or `rangeFormatting` for a selection when it offers that, and otherwise runs the language's first installed formatter from `formatters.rs` (data like the debuggers: `assets/default-formatters.toml`, each with an optional `install`; the user's `formatters.toml` adds or replaces by `key`), fed the buffer on stdin; a formatter chosen on the language's page goes ahead of the server. Either way the new text goes in as one undo step touching only changed lines (`text_edits.rs`, shared with rename), the cursor kept on its token. Each language's page in Settings > Languages turns on format on save for it (`[formatting] on_save`), and Settings > Editor trimming trailing whitespace and a final newline (both off by default). The project's `.editorconfig` (`editorconfig.rs`, read up to `root = true`) wins over both: its `indent_style`, `indent_size` and `tab_width` over the indentation detected on opening (`indentation.rs`), and its `trim_trailing_whitespace`, `insert_final_newline` and `end_of_line` (`lf` or `crlf`) on save; a formatter that takes over 2 s is given up on, the file saved as it is, and the status bar says so. Nothing is formatted while a change is under review. Completions (`workspace/completions.rs`) show as a name is typed, after one of the server's trigger characters, and in a struct literal after the space or new line that follows its `{` or a `,`, when all the server offers there is fields (`completions::only_fields`; not on `{` or `,` itself, so Enter still starts a line); Show Completions (⌃Space) lists what fits at the cursor. `snippets.rs` adds Jig's snippets to the list, prefix (`for`) and postfix (`users.var`); `workspace/snippets.rs` fills a taken snippet in place by place with Tab and Shift-Tab. Line shortcuts (`lines.rs`, `workspace/line_edits.rs`): move line ⌥↑/⌥↓, duplicate ⇧⌘D, delete ⇧⌘⌫, select ⌘L, new line below/above ⌘↩/⇧⌘↩, bound in the `CodeEditor` context so other inputs keep their keys; Go to Line ⌃G (`workspace/go_to_line.rs`, `42` or `42:5`); code font ⌘=/⌘-/⌘0. Typing a bracket or quote over a selection wraps it and keeps it selected, one undo step (a vendored-editor patch; without a selection the pair auto-closes). The bracket next to the cursor and its pair get a box each (`brackets.rs`, a text scan skipping strings and comments, since the highlighter's syntax tree isn't reachable), and the indent guide of the cursor's block is drawn stronger (`indentation::active_guide`, a vendored-editor patch); `workspace/brackets.rs` updates both as the cursor moves. The name at the cursor, or a selected name, gets its other uses in the file filled in softly after 150 ms (`workspace/occurrences.rs`): where the server says (`textDocument/documentHighlight`), or its whole-word matches without one; typing clears them. `workspace/status_bar.rs` shows cursor position, indentation (`indentation.rs`), encoding and language.
- Updates (`update.rs`, `update/release.rs`, `update/install.rs`): shortly after starting and once a day (Settings > Updates, `[updates] automatic`), or from Jig > Check for Updates…, the About Jig window (`about_window.rs`: icon, version, a Check for Updates button) and Settings' Check Now, Jig asks GitHub for the latest release of `lucasdias111/jig`, downloads this computer's build (`Jig-macos-arm64.zip`, `Jig-linux-x86_64.tar.gz`, `Jig-windows-x86_64.zip`) and checks its `.minisig` against the minisign key built in; the signature's trusted comment must read `jig <version> <asset>`, so an older signed build can't pass as the latest. Nothing installs until Restart to Update (status bar, or the dialog a manual check shows), which asks about unsaved changes as Quit does, unpacks the build beside the installed one, swaps it in (the whole `Jig.app` on macOS; the executable elsewhere, Windows keeping `Jig.exe.old` until the next start) and starts it on the open project. A build from source (`target/…`), a translocated app or a folder Jig can't write to offers the download page instead. `.github/workflows/release.yml` builds all three on a `v*` tag that must match Cargo.toml's version, and signs them with the `MINISIGN_KEY` secret. Each archive (and `Jig.app`'s Resources) carries `LICENSE` and `THIRD-PARTY-NOTICES.txt`, the dependencies' licences written by `script/third-party-notices.sh` with cargo-about; `script/licenses/about.toml` lists the licences accepted (a dependency under another fails the release) and clarifies crates whose licence files Cargo doesn't name (GPUI Kit's Lucide icons, `tree-sitter-graphql`).
- Shortcuts: `shortcuts.rs` lists every shortcut Settings > Keyboard can change (id, label, default keys, contexts, action). It snapshots the keymap without them at startup and rebuilds it, and the menus, whenever `[shortcuts]` in `settings.toml` changes (`id = "cmd-shift-d"`, `""` for none). The page (`settings_window/shortcuts_page.rs`) records keys through a keystroke interceptor, so the keys pressed don't also run. New user-facing shortcuts go in that table, not in `workspace::key_bindings`.
- Run configurations (IntelliJ-style): `run_configs.rs` loads the project's `.jig/run.toml` (`[[run]]` with `name`, `command` run through `/bin/sh` (`cmd` on Windows), optional `cwd`, `env`) and detects Cargo binaries/examples, `package.json` scripts, Go modules, Maven main classes (run with `exec:java`, debugged by their file) and Gradle's `run`; a file entry replaces a detected one of the same name. `run_output.rs` runs one in its own process group (on Windows its process tree; Stop kills what it started), keeps ANSI colours and links `file:line:col`. Its output can be selected with the mouse (double click a word, triple a line, Shift extends) and copied with ⌘C, ⌘A or the right-click menu. `run_picker.rs` is the ⌃⌥R picker; `workspace/run.rs` has ⌃R run, ⌘F2 stop, ⌘J output panel, and the title-bar controls. Changed files are saved before a run. No stdin.
- Debugger (⌃D) over the Debug Adapter Protocol, generic like nvim-dap: debuggers are data. `assets/default-debuggers.toml` has the built-ins (LLDB for Rust, C, C++, Swift and Zig with `lldb-dap`, TypeScript/JavaScript with js-debug, Python with debugpy, Go with Delve, Java with java-debug in jdtls) and documents every field; the user's `~/.config/jig/debuggers.toml` adds more or replaces one by `key` (Run → Edit Debuggers). An entry says how to start the adapter (`adapter` on stdio or `server` with `${port}`, run in the configuration's folder; or `lsp` for one living in a language server Jig runs: `lsp_bundles` are passed to it in `initialize`, `lsp_start` is the `workspace/executeCommand` answering with the port, see `lsp_debug.rs`), which run configurations it takes (`commands` prefixes, `program` `extensions`, `executables`), how to check and `install` it (a shell command; Settings' Install button runs it into Jig's debuggers folder, whose `bin` is searched like the PATH; `uninstall` lists what it put there, which Settings' Uninstall moves to the Trash), and a `launch` template with `${program}`, `${args}`, `${command}`, `${env}` and the like. `debuggers.rs` loads, merges and fills them in; the only per-debugger code is a few tool lookups (`${lldb_dap}` incl. Xcode and `lldb-dap-18`-style names, `${js_debug}`, `${node}`, `${lldb_rust_formatters}`) Java's values from jdtls (`${java_main_class}`, preferring the run configuration's `program` or the open file, `${java_project}`, `${java_class_paths}`, `${java_module_paths}`) and the Cargo builder (`build = "cargo"`: `cargo build --message-format=json-render-diagnostics`, debug the reported executable). `debug_target.rs` picks a configuration's debugger (run.toml `debugger`, else `program` extension, else longest `commands` match). Each language's page in Settings > Languages turns its debugger on (`[debugging] enabled`, default `rust`); only files of enabled languages get the breakpoint column. `dap.rs` is the client: stdio or TCP, several connections per session (js-debug runs the program in a child session it asks for with `startDebugging`), all messages tagged by connection on one channel; the session is a state machine over them, polled like run output. `workspace/breakpoints.rs`: ⌘F8 or a gutter click toggles a breakpoint, kept as a range decoration with a gutter dot (a vendored-editor patch) so it moves with edits; remembered in `~/.config/jig/breakpoints.json`. `workspace/debug.rs`: resume F9/⌥⌘R, step over F8, into F7, out ⇧F8, Stop ⌘F2; paused line highlighted; the output panel gets Debugger (call stack, variables tree) and Console views. Live tests use real debuggers (macOS may ask once to allow debugging): `cargo test -p jig-app tests::debug::debug_live -- --ignored`, `lldb_dap_live`, and with `JIG_DEBUGGERS_DIR=<folder with them installed>`: `debug_typescript_live`, `debug_python_live`, `debug_go_live`, and with `JIG_LIVE_LSP=1 JIG_CACHE_DIR=<scratch>` too, `debug_java_live`; `built_in_installers_live` runs the install commands. `server_installers_live` and `formatter_installers_live` (`-- --ignored --nocapture`, `JIG_LIVE_TOOLS=marksman,shfmt` for just some) install every server and formatter into a scratch folder, the formatters formatting a sample.
- Git, through the `git` command line (`git.rs`, no GUI code; the user's config, credential helpers and SSH agent apply, and git never gets a terminal to prompt on). `workspace/git.rs`: each tab's gutter has change bars against the last commit (green added, blue changed, red wedge for removed lines; a vendored-editor patch, `set_line_changes`), worked out again on every edit from the committed text, which is re-read when the window comes forward, on save, and after Jig's own git actions. Clicking a bar shows the old lines under the change, with Revert (one undo step). A narrow activity bar at the window's left edge (`workspace/sidebar.rs`) switches the sidebar (below the title bar) between Files and Git, and clicking the shown view's button collapses it; it slides open and shut. A gear at its foot opens Settings; with no project open there's no activity bar, so the gear floats in the window's bottom-left corner. The Git view (⌃⇧G, `git_panel.rs`; kept current while it shows by watching the repository, `workspace/git/watch.rs`, and when the window comes forward) has fetch, pull, push (giving a new branch an upstream), a Branch button, a commit message, and staged and unstaged files to open, stage or unstage. Each file has a check (tracked changes start checked, untracked files don't): each section's header stages or unstages its checked files and nothing else (there's no Stage All, which would sweep in build folders), and ↩ or Commit commits exactly the checked files (`git commit --only`), leaving anything else staged as it was. Untracked folders are one entry; paths go to git on stdin. The branch in the status bar, the Git view's Branch button, or Git > Switch Branch… (`branch_picker.rs`), checks out a local or remote branch or creates one; its first row, New Branch…, and Git > New Branch… open it as just a name field for a branch started from the current one; changed files are saved first, and open tabs without unsaved changes reload afterwards.

## Providers

- No provider by default: Jig favours no vendor. The built-in `config.toml` connects none and picks no model (`agent = ""`, read as none), so a conversation on OpenCode says to connect one in Settings > Providers (other agents bring their own sign-in and models). The first provider connected starts the agent on one of its fast models once it lists them (`ProviderTemplate::fast`, e.g. Haiku, mini, flash; a local server's first model), never over a model already picked (`providers::start_on_a_model`). OpenCode Go is one provider among the others (Anthropic format, an `x-opencode-session` header). API keys never go in `config.toml`: one typed in Settings goes in the system keychain (macOS Keychain, Windows Credential Manager; elsewhere a 0600 `keys.toml`) and wins over the `api_key_env` variable.

## Working on Jig

```sh
cargo run -p jig-app -- <file-or-folder>
cargo test                       # ~600 tests, including headless UI tests
cargo clippy --all-targets       # keep at zero warnings
cargo fmt
cargo deny check                 # advisories, licences, sources (deny.toml); CI runs it
script/bundle-macos.sh           # builds target/Jig.app
```

- Live tests and tools that call real agents and models are opt-in: `cargo test -p jig-app agent_live -- --ignored` (needs OpenCode), `JIG_SERVERS_DIR=<scratch> cargo test -p jig-app server_install_live -- --ignored` (installs YAML's server with npm), `cargo run -p jig-ai --example agent -- <dir> "<prompt>" [<ACP agent command>…]`. They cost money; don't run them in loops.
- Depend on `gpui-kit` only, pinned exactly (`=0.7.0`). GPUI distributions can't be mixed.
- UI tests live in `workspace/tests/`, one file per feature, with the shared helpers in `workspace/tests.rs`. They open a real window on GPUI's test platform: `open(cx, path)`, then `step(cx, window, |window, cx| …)` to press keys and let effects settle. Type and press in separate steps when the list needs to refilter in between.
- Match the surrounding style: doc comments say why, in plain sentences; names over comments; small focused functions. User-facing text is short, plain and specific ("Save the file first, so the agent knows which project it's in.").
- Cross-platform: GPUI runs on macOS, Linux and Windows, and CI builds all three. Keep macOS-only touches behind `cfg!(target_os = "macos")` with a plain fallback, bind keys with `secondary-` (⌘ on macOS, Ctrl elsewhere), gate Unix APIs (`std::os::unix`, `libc`) with `#[cfg(unix)]`, start every other program with `.no_window()` (`jig_process::NoWindow`; release builds are windowed on Windows, so a console program would otherwise flash a window of its own), and one that could hang (an installer, git over the network) with `jig_process::output_within`, which stops it and what it started after a limit, and put caches and config where each OS expects them.
- New languages: enable the grammar feature in the root `Cargo.toml`, or, for a grammar GPUI Kit has no feature for, add its crate to `jig-app`'s `Cargo.toml` and a line to `languages/grammars.rs` (its own highlights, or the `.scm` file its crate ships copied into `languages/queries/`; older Neovim capture names are mapped onto the theme's). The crate must build on `tree-sitter-language` or `tree-sitter >= 0.21`, never pull in a second tree-sitter, and resolve beside GPUI Kit's pins; check what it adds to the release binary, since some parse tables are 5-15 MB. Then add it, and a server and formatter if there are any, to `assets/default-languages.toml` (`starter = true` puts it in everyone's list from the start; otherwise it's added from the Library). Users can't load grammars of their own.
- When a feature lands or changes, update this file if it changes the concept or the layout.
