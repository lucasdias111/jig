# AGENTS.md

Jig is a macOS-first code editor (it also builds on Linux and Windows) where AI works through **jigs**, small commands run at the cursor, not through a chat or an agent somewhere else. You select code, press ⌘K, pick a jig or type a prompt, and the change shows inline for you to accept or reject. Jig sends this file with every Jig-mode run, and OpenCode reads it in Agent mode, so keep it short and current.

## The concept

**AI as a tool, not a colleague.** IDE refactorings are precise but fixed; agents are open-ended but take you away from the code. Jig uses the refactoring interaction with AI behind it. The name is from woodworking: a jig guides precise, repeatable cuts by hand, and each saved command is one. In the UI, files and docs they're "jigs"; in the code they're still presets and commands (`Preset`, `jig-commands`). OpenCode's own commands are a different thing; call them "OpenCode commands".

Principles:

- **Near the code.** Every interaction is anchored to the cursor. No side panels, except an agent conversation you pin to the side yourself.
- **You decide.** Every change is previewed and needs an explicit accept. Nothing reaches the disk unreviewed, in either mode, and the agent's shell commands, web access and subagents wait for a go-ahead too.
- **Brief.** In Jig mode the AI answers in one sentence of at most 20 words, or not at all. The agent may say more.
- **Keyboard first.** Few shortcuts, each obvious.
- **Clean and Mac-like.** The code is the interface. Restrained colour, floating panels, follows system light/dark.

### Two modes

The input (⌘K) has a **Jig | Agent** switch at the top. **Tab** flips it. Each mode ("lane" in the code) has its own colour and icon everywhere it appears (switch, input, highlight, bubble tag), so you can always tell which one is running.

- **Jig** (theme primary/soft green, pencil). Where jigs run. One model call that rewrites only the target: the selection (or current line), the cursor, or the whole file, per the jig's `scope`. It sees the file and the nearest `AGENTS.md`, nothing else, and touches nothing else. Should take 2-5 s.
- **Agent** (theme info/orange, bot). A coding-agent harness at the code, agnostic about the agent: Settings > Agent picks it from the agents listed as data (`agents.rs`; `assets/default-agents.toml` has OpenCode, Claude Code, Codex and Gemini CLI and documents every field; the user's `agents.toml` adds any agent that speaks the Agent Client Protocol, or replaces one by `key`; Install runs its `install` into Jig's agents folder, whose `node_modules/.bin` and `bin` are searched with the PATH; `[agent] use` in `settings.toml`). OpenCode (`kind = "opencode"`, the default) runs through Jig's own client (`opencode serve`, `jig-ai/src/agent.rs`), with the Agent model from Settings > Model, edits always set to ask and questions with choices. Every other agent runs over ACP (`jig-ai/src/acp.rs`): one process per agent, JSON-RPC on stdio, Jig as a client that reads files from disk and writes them only after review (`fs/write_text_file`; an edit already allowed by permission is written without asking twice). An agent that answers "Authentication required" (`acp::SignInNeeded`) gets its sign-in methods offered in the conversation: a `terminal` one opens the system terminal with the agent's own login (`agent::open_in_terminal`, a `.command` file on macOS), then Enter tries again; any other is `authenticate`d, and the turn is sent again. `jig-ai/src/harness.rs` puts both behind one `Backend`/`Session`. The agent reads and edits the whole project with its own skills, commands and instructions file. Each edit it asks about (OpenCode's diff; ACP's permission request with a `diff` or the tool's old and new text; or a file it hands Jig to write) arrives *before* it's written and opens in its file's tab as a normal preview. An ACP agent set to edit without asking can't be stopped; the transcript says "Edited x without asking". The built-ins are set up to ask: Claude Code's default mode does, Codex starts `read-only`. Enter/Tab accepts (OpenCode writes it), Esc/⌘Z rejects (the agent is told and may retry). The conversation is kept apart from ⌘K's runs (`Workspace::chat` beside `run`): a jig can run, and its bubble show, while it's open; Esc dismisses the jig's bubble first. While it's docked, ⌘K opens the input on Jig, with the switch's Agent side greyed ("the agent is in its panel"); ⌥⌘K and the panel's history button still open the earlier conversations. Starting another conversation replaces the one on screen, undoing an edit of its still under review. A conversation belongs to the project, not the file it started from: it works in the folder open in the sidebar (or the file's repository when there's none, `Workspace::agent_project`), its header names that project, and it stays open and working across tab switches; an edit it proposed waits in its file's tab (Esc or clicking the file in the conversation goes back to it, and accepting it settles it there). A saved file isn't needed once a folder is open. The run is a floating conversation at the code (`jig-commands/src/chat.rs`): what was asked, the agent's replies, each edit taken or rejected, and a reply box once the agent answers. It opens to the right of the code it's about when the window has room, below the cursor otherwise. Drag it by its header to move it (it then stays put) or by its corner to resize it; its pin button docks it to the window's right edge, full height, beside the code, on the editor's own background; docked, its left edge drags to resize it, and the next conversation opens docked at that width until it's unpinned. Replies render Markdown. A reply continues the same OpenCode session, and a reply like `/review main` runs that OpenCode command in it. Shell commands, web fetches and searches, and subagents (`task`) ask by default; Settings > Agent (`settings_window/agent_page.rs`, `[agent]` in `settings.toml`, `jig_ai::agent::Permissions`) sets each to ask, allow or don't allow, and turns the question tool off. The rules are re-sent to OpenCode at the start of every turn, so a change applies from the next one, earlier conversations included; edits always ask and outside the project is always denied. Asked, the conversation shows what it wants to run with three buttons: Allow (Enter/Tab, once), Always allow (⌘↩; OpenCode's `always` reply, naming the patterns it will remember, or an ACP agent's `allow_always` option; an agent with neither has Jig allow that kind of request for the rest of the conversation) and Deny (Esc). What ran is listed in the transcript either way. Over ACP, the settings map onto tool kinds (`execute` is shell, `fetch` the web, reading and searching need no go-ahead, anything else asks). With OpenCode's question tool on (the default): the question shows with numbered options, answered by clicking one or typing a number or your own words in the reply box (Esc declines). Edits and requests from its subagents come through the same way. Nothing outside the project. Esc with nothing waiting stops the agent's turn; Esc again closes the conversation. 15-60 s.
- **Earlier conversations.** Every conversation stays with its agent. OpenCode's are titled with what was first asked (`metadata.jig`; older Jig sessions are known by their edit-asks rule, and the user's own OpenCode sessions aren't listed). An ACP agent's come from `session/list` with its own titles, and are picked up with `session/load`, as far as the agent can; its `/` commands are the ones it last announced (`available_commands_update`), so they show once a conversation with it has started. In Agent mode the input lists them under **Conversations**, latest first, filtered by the typed words; Enter on one picks it up with its transcript (`AgentSession::open`, `history` reads it back). ⌥⌘K (Agent Conversations…, in the Edit menu and Settings > Shortcuts) and the conversation's history button open the input in Agent mode.

A jig can always run on the agent with `agent = true`; the switch then shows Agent with "set by this jig". In Agent mode, typed text is a message for the agent, never a jig: `/` lists `/jig` and OpenCode's commands and skills (`GET /command`; text after the name is its arguments, run with `POST /session/:id/command` in a new conversation), and `/jig docs: terse` runs a jig on the agent.

### The input

- ⌘K, the Jig button in the title bar (a toggle: pressed while the input is open, and it or ⌘K again closes it; the input grows out of it and shrinks back, `workspace/palette_motion.rs`), or the sparkle button that appears just right of a selection while the code has focus (`workspace/selection_button.rs`; hidden while a run, preview or panel is open, and turned off with Settings > Appearance > Jig button on selections).
- The typed text is listed first under **Prompt**, matching jigs below under **Jigs**. Enter takes a jig only when the text clearly names it (its name or one of its words starts with the text); otherwise it runs the text as a prompt. ↑↓ pick either way. When the text is how the highlighted jig's name starts, the rest of the name shows in grey after it, and → or End at the end of the text completes it (Tab stays the lane switch). ⌘↩ saves the typed text as a jig.
- **Notes**: `docs: terse, no examples` runs the jig matching "docs" with the note "terse, no examples". The colon only counts when the text before it matches a jig. Typing `:` on a jig chosen with the arrows completes its name (`Simplify: `). Jigs with `comment = "optional" | "required"` open a note step on Enter when no note was typed.
- The footer says what will happen, e.g. "Edits the selection · sees this file, AGENTS.md".

### Review

A change goes into the buffer provisionally: highlighted, file read-only, one undo step. The model returns the whole new region, so Jig diffs it line by line (`jig-app/src/diff.rs`): only lines that differ are edited, only new lines are highlighted, and the bubble lists only lines actually removed. Tab/Enter accepts, Esc or ⌘Z rejects. A reply that changes nothing (e.g. an explanation) just shows its message.

## Layout

Rust workspace, edition 2024, toolchain pinned in `rust-toolchain.toml`.

- `crates/jig-app`: the binary (`Jig`). Window, workspace, tabs, file tree (`file_tree.rs`; right-click for New File/Folder, Rename (F2), Move to Trash (⌘⌫), Copy Path and Reveal; open tabs follow a rename and close when their file is trashed, unless unsaved), Go to File (⌘P), Find (⌘F) and Find and Replace (⌥⌘F) in the file (`find_panel.rs`, a floating panel over the editor's search engine, which is built `searchable(false)`; it starts from a short one-line selection and won't replace while a change is under review), Find in Files (⇧⌘F), menus, settings window, themes. `workspace/file_watch.rs` watches the folders of open files and shows changes made outside Jig in tabs without unsaved changes, as one undo step keeping the cursor (also checked when the window comes forward). `workspace/commands.rs` runs Jig-mode jigs and prompts; `workspace/agent.rs` runs Agent mode: conversations, their edits and requests, and picking up earlier ones; `agent.rs` owns the shared OpenCode server; `project.rs` finds the project root and `AGENTS.md`; `diff.rs` is the preview diff. `lsp.rs` runs language servers (not bundled; one that isn't installed is skipped) for ⌘-click go to definition and autocomplete, with `definitions.rs` guessing declarations and `completions.rs` offering words from the file when no server answers. Problems servers report (`publishDiagnostics`, `lsp/diagnostics.rs`) are kept per file, open or not, under the file's real path as a URI (servers write URIs their own way, e.g. `file:///c%3A/…`), with reports about text that has since changed dropped; `workspace/diagnostics.rs` shows them: squiggles in the theme's status colours, the message in a small panel on hover, error and warning counts in the status bar (click to step), and Next/Previous Problem (⌥F8/⇧⌥F8). They move with edits until the server reports again (a vendored-editor patch). No server, nothing shown. `workspace/hover.rs` (parsing in `hover.rs`): resting the pointer on a name for 500 ms, or ⌘I (Show Hover) at the cursor, asks `textDocument/hover` and shows the Markdown in a panel below it (code blocks highlighted), with any problem there above it; typing hides it, as do Esc and the cursor moving. Typing `(` or `,` in a call asks `textDocument/signatureHelp` and shows the signature above the cursor, the active parameter in bold, until `)`, Esc or the cursor leaves the call. The editor draws neither (a vendored-editor patch: Jig draws the hover, sets its delay and hears what's typed), and neither shows while the palette, a review or the run's bubble or conversation covers its spot. Right-clicking the code (`workspace/code_menu.rs`) offers Go to Definition, Find All References (⇧F12), Rename Symbol (F2), Run Jig…, the clipboard and Toggle Line Comment (⌘', or ⌘/). Rename (`workspace/rename.rs`, field in `field_box.rs`) asks the server for `textDocument/rename` and makes its edits in each file's buffer, opening tabs behind the current one for files that aren't open, unsaved and one undo step per file; without a server it renames whole-word uses in the file. Format Document (⇧⌥F, Edit menu, right-click; `workspace/format.rs`) asks the server for `textDocument/formatting`, or `rangeFormatting` for a selection when it offers that, and otherwise runs the language's first installed formatter from `formatters.rs` (data like the debuggers: `assets/default-formatters.toml` has rustfmt, Prettier, gofmt, Ruff, Black, google-java-format and Taplo; the user's `formatters.toml` adds or replaces by `key`), fed the buffer on stdin. Either way the new text goes in as one undo step touching only changed lines (`text_edits.rs`, shared with rename), the cursor kept on its token. Settings > Languages turns on format on save per language (`[formatting] on_save`), trimming trailing whitespace and a final newline (both off by default); a formatter that takes over 2 s is given up on, the file saved as it is, and the status bar says so. Nothing is formatted while a change is under review. `snippets.rs` adds Jig's snippets to the list, prefix (`for`) and postfix (`users.var`); `workspace/snippets.rs` fills a taken snippet in place by place with Tab and Shift-Tab. Line shortcuts (`lines.rs`, `workspace/line_edits.rs`): move line ⌥↑/⌥↓, duplicate ⇧⌘D, delete ⇧⌘⌫, select ⌘L, new line below/above ⌘↩/⇧⌘↩, bound in the `CodeEditor` context so other inputs keep their keys; Go to Line ⌃G (`workspace/go_to_line.rs`, `42` or `42:5`); code font ⌘=/⌘-/⌘0. Typing a bracket or quote over a selection wraps it and keeps it selected, one undo step (a vendored-editor patch; without a selection the pair auto-closes). The bracket next to the cursor and its pair get a box each (`brackets.rs`, a text scan skipping strings and comments, since the highlighter's syntax tree isn't reachable), and the indent guide of the cursor's block is drawn stronger (`indentation::active_guide`, a vendored-editor patch); `workspace/brackets.rs` updates both as the cursor moves. `workspace/status_bar.rs` shows cursor position, indentation (`indentation.rs`), encoding and language.
- Shortcuts: `shortcuts.rs` lists every shortcut Settings > Shortcuts can change (id, label, default keys, contexts, action). It snapshots the keymap without them at startup and rebuilds it, and the menus, whenever `[shortcuts]` in `settings.toml` changes (`id = "cmd-shift-d"`, `""` for none). The page (`settings_window/shortcuts_page.rs`) records keys through a keystroke interceptor, so the keys pressed don't also run. New user-facing shortcuts go in that table, not in `workspace::key_bindings`.
- Run configurations (IntelliJ-style): `run_configs.rs` loads the project's `.jig/run.toml` (`[[run]]` with `name`, `command` run through `/bin/sh` (`cmd` on Windows), optional `cwd`, `env`) and detects Cargo binaries/examples, `package.json` scripts, Go modules, Maven main classes (run with `exec:java`, debugged by their file) and Gradle's `run`; a file entry replaces a detected one of the same name. `run_output.rs` runs one in its own process group (on Windows its process tree; Stop kills what it started), keeps ANSI colours and links `file:line:col`. Its output can be selected with the mouse (double click a word, triple a line, Shift extends) and copied with ⌘C, ⌘A or the right-click menu. `run_picker.rs` is the ⌃⌥R picker; `workspace/run.rs` has ⌃R run, ⌘F2 stop, ⌘J output panel, and the title-bar controls. Changed files are saved before a run. No stdin.
- Debugger (⌃D) over the Debug Adapter Protocol, generic like nvim-dap: debuggers are data. `assets/default-debuggers.toml` has the built-ins (Rust/C/C++ with `lldb-dap`, TypeScript/JavaScript with js-debug, Python with debugpy, Go with Delve, Java with java-debug in jdtls) and documents every field; the user's `~/.config/jig/debuggers.toml` adds more or replaces one by `key` (Run → Edit Debuggers). An entry says how to start the adapter (`adapter` on stdio or `server` with `${port}`, run in the configuration's folder; or `lsp` for one living in a language server Jig runs: `lsp_bundles` are passed to it in `initialize`, `lsp_start` is the `workspace/executeCommand` answering with the port, see `lsp_debug.rs`), which run configurations it takes (`commands` prefixes, `program` `extensions`, `executables`), how to check and `install` it (a shell command; Settings' Install button runs it into Jig's debuggers folder, whose `bin` is searched like the PATH), and a `launch` template with `${program}`, `${args}`, `${command}`, `${env}` and the like. `debuggers.rs` loads, merges and fills them in; the only per-debugger code is a few tool lookups (`${lldb_dap}` incl. Xcode and `lldb-dap-18`-style names, `${js_debug}`, `${node}`, `${lldb_rust_formatters}`) Java's values from jdtls (`${java_main_class}`, preferring the run configuration's `program` or the open file, `${java_project}`, `${java_class_paths}`, `${java_module_paths}`) and the Cargo builder (`build = "cargo"`: `cargo build --message-format=json-render-diagnostics`, debug the reported executable). `debug_target.rs` picks a configuration's debugger (run.toml `debugger`, else `program` extension, else longest `commands` match). Settings → Languages → Debugging turns each on (`[debugging] enabled`, default `rust`); only files of enabled languages get the breakpoint column. `dap.rs` is the client: stdio or TCP, several connections per session (js-debug runs the program in a child session it asks for with `startDebugging`), all messages tagged by connection on one channel; the session is a state machine over them, polled like run output. `workspace/breakpoints.rs`: ⌘F8 or a gutter click toggles a breakpoint, kept as a range decoration with a gutter dot (a vendored-editor patch) so it moves with edits; remembered in `~/.config/jig/breakpoints.json`. `workspace/debug.rs`: resume F9/⌥⌘R, step over F8, into F7, out ⇧F8, Stop ⌘F2; paused line highlighted; the output panel gets Debugger (call stack, variables tree) and Console views. Live tests use real debuggers (macOS may ask once to allow debugging): `cargo test -p jig-app tests::debug::debug_live -- --ignored`, `lldb_dap_live`, and with `JIG_DEBUGGERS_DIR=<folder with them installed>`: `debug_typescript_live`, `debug_python_live`, `debug_go_live`, and with `JIG_LIVE_LSP=1 JIG_CACHE_DIR=<scratch>` too, `debug_java_live`; `built_in_installers_live` runs the install commands.
- Git, through the `git` command line (`git.rs`, no GUI code; the user's config, credential helpers and SSH agent apply, and git never gets a terminal to prompt on). `workspace/git.rs`: each tab's gutter has change bars against the last commit (green added, blue changed, red wedge for removed lines; a vendored-editor patch, `set_line_changes`), worked out again on every edit from the committed text, which is re-read when the window comes forward, on save, and after Jig's own git actions. Clicking a bar shows the old lines under the change, with Revert (one undo step). A narrow activity bar at the window's left edge (`workspace/sidebar.rs`) switches the sidebar (below the title bar) between Files and Git, and clicking the shown view's button collapses it; it slides open and shut. A gear at its foot opens Settings; with no project open there's no activity bar, so the gear floats in the window's bottom-left corner. The Git view (⌃⇧G, `git_panel.rs`; kept current while it shows by watching the repository, `workspace/git/watch.rs`, and when the window comes forward) has fetch, pull, push (giving a new branch an upstream), a Branch button, a commit message, and staged and unstaged files to open, stage or unstage. Each file has a check (tracked changes start checked, untracked files don't): each section's header stages or unstages its checked files and nothing else (there's no Stage All, which would sweep in build folders), and ↩ or Commit commits exactly the checked files (`git commit --only`), leaving anything else staged as it was. Untracked folders are one entry; paths go to git on stdin. The branch in the status bar, the Git view's Branch button, or Git > Switch Branch… (`branch_picker.rs`), checks out a local or remote branch or creates one; its first row, New Branch…, and Git > New Branch… open it as just a name field for a branch started from the current one; changed files are saved first, and open tabs without unsaved changes reload afterwards.

- `crates/jig-editor`: `EditorHandle`, the only way the command layer touches the editor (text, selection, cursor, screen anchor, one-undo-step edits, highlights). Keeps the door open to replacing GPUI Kit's editor.

- Providers in the app: `providers.rs` holds the config, keys and each provider's model list as a global that workspaces observe. Settings > Model connects the major providers (paste a key, or switch on a local server) and picks each lane's model from what the connected providers list. `agent.rs` restarts the shared OpenCode server when the agent's provider config changes; runs underway keep the old one.

Per project: `.jig/run.toml` (run configurations). User files live in `~/.config/jig/`: `debuggers.toml` (own debuggers; same key replaces a built-in), `agents.toml` (own agents for Agent mode; same key replaces a built-in), `formatters.toml` (own formatters; same key replaces a built-in, and yours come first), `jigs.toml` (own jigs, `[[jig]]`; same name replaces a built-in; an older `commands.toml` with `[[command]]` still reads), `config.toml` (providers, and `quick` (Jig mode) / `agent` as `provider/model`; the agent follows quick when unset; older `default` + `model` and `agent_model` still read), `keys.toml` (API keys, only where there's no system keychain), `settings.toml` (hidden jigs under `[jigs]`, changed shortcuts under `[shortcuts]`, what saving does under `[formatting]`, the agent's permissions under `[agent]`), `snippets.toml` (own snippets; same name replaces a built-in), `recent.toml` (projects for the home page), `sessions.toml` (each project's open files and showing tab, saved as tabs change and reopened when its folder opens on an empty window; `session.rs`, `workspace/session.rs`).

## The Jig mode contract

- Prompt (`jig-ai/src/prompt.rs`): instruction, optional note, optional `<diagnostics>` (the problems on the target's lines, `line N, severity: message`, for jigs with `diagnostics = true` such as Fix), language, file name, `AGENTS.md` as `<project_rules>`, and the file with the region marked `<<<SELECTION>>>…<<<END>>>` or `<<<CURSOR>>>`. Files over 24 KB are cut to whole lines around the region. The reply format is repeated after the file.
- Reply: `{"replace": "<new text for the region>", "message": "<≤20 words>"}`. Anthropic-format providers must return it through a forced `apply_edit` tool call; OpenAI-format ones use JSON mode. Anything that doesn't parse is an error and never changes the buffer.
- Thinking is off by default (`thinking: {type: disabled}` / `reasoning_effort: none`); with it on, reasoning models took 30-75 s and sometimes returned nothing. `thinking = true` on a provider turns it back on.
- Default model for both lanes: OpenCode Go `qwen3.8-flash` (Anthropic format, needs `OPENCODE_API_KEY` and an `x-opencode-session` header). API keys never go in `config.toml`: one typed in Settings goes in the system keychain (macOS Keychain, Windows Credential Manager; elsewhere a 0600 `keys.toml`) and wins over the `api_key_env` variable.

## Working on Jig

```sh
cargo run -p jig-app -- <file-or-folder>
cargo test                       # ~380 tests, including headless UI tests
cargo clippy --all-targets       # keep at zero warnings
cargo fmt
script/bundle-macos.sh           # builds target/Jig.app
```

- Live tests and tools that call real models are opt-in: `cargo test -p jig-app agent_live -- --ignored` (needs OpenCode), `cargo run -p jig-ai --example live -- --file <path> --lines 10-20` (times one Jig-mode run), `cargo run -p jig-ai --example agent -- <dir> "<prompt>" [<ACP agent command>…]`. They cost money; don't run them in loops.
- Depend on `gpui-kit` only, pinned exactly (`=0.7.0`). GPUI distributions can't be mixed.
- UI tests live in `workspace/tests/`, one file per feature, with the shared helpers in `workspace/tests.rs`. They open a real window on GPUI's test platform: `open(cx, path)`, then `step(cx, window, |window, cx| …)` to press keys and let effects settle. Type and press in separate steps when the list needs to refilter in between.
- Match the surrounding style: doc comments say why, in plain sentences; names over comments; small focused functions. User-facing text is short, plain and specific ("Save the file first, so the agent knows which project it's in.").
- Cross-platform: GPUI runs on macOS, Linux and Windows, and CI builds all three. Keep macOS-only touches behind `cfg!(target_os = "macos")` with a plain fallback, bind keys with `secondary-` (⌘ on macOS, Ctrl elsewhere), gate Unix APIs (`std::os::unix`, `libc`) with `#[cfg(unix)]`, and put caches and config where each OS expects them.
- New languages: enable the grammar feature in the root `Cargo.toml` and add it to `languages::BUNDLED`.
- When a feature lands or changes, update this file if it changes the concept, the layout or the contract.
